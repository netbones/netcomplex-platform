**Assess the dual REST/tRPC settings surface and produce a consolidation roadmap.**

Purpose: The settings system is served through two parallel API surfaces — 5 tRPC procedures and 8 REST endpoints. Output:

- `REST-TRPC-ASSESSMENT.md` — documentation of current state, gaps, and migration plan

**This is a research+planning deliverable. No code changes in this plan.**

  <files>

  <action>
Produce a comprehensive audit table documenting every settings operation across both surfaces.

For each operation (list, get, upsert, delete, contact, page-flags, services-config, provider-reg-mode), document:

| Aspect             | REST                           | tRPC                                           |
| ------------------ | ------------------------------ | ---------------------------------------------- |
| Endpoint/Procedure | `/api/settings/` GET           | `settingsRouter.listSettings`                  |
| Access Control     | `hasPermission(role, 'admin')` | `privilegedProcedure` + inline `hasPermission` |
| Audit Log          | Yes (POST) / No (GET)          | Yes (mutations only)                           |
| Revalidation       | Yes (since phase 6 fix)        | Yes (`revalidateAdminChanges`)                 |
| Rate Limiting      | Yes (POST/PATCH)               | No                                             |
| AssistScope Guard  | Yes (POST/PATCH)               | No                                             |
| Cache (ISR)        | No                             | No (tRPC is not cached)                        |
| Consumer           | Admin dashboard widget         | OpenAPI (external), existing tRPC callers      |

Then classify each operation:

- **Canonical on REST**: Operations only available via REST (page-flags, services-config, provider-reg-mode)
- **Canonical on tRPC**: Operations only available via tRPC (listSettings, deleteSetting)
- **Duplicated**: Both surfaces exist with different guarantees (upsert=POST/PATCH vs upsertSetting)

List gaps explicitly:

- tRPC upsert has `revalidateAdminChanges()` → REST now has it too (fixed)
- REST POST has `rateLimitByUser` → tRPC upsert does not
- REST POST has `requireAssistScope` → tRPC upsert does not
- tRPC `deleteSetting` has no REST equivalent (soft-delete only via tRPC)
- Page-flags/services-config/provider-reg-mode have no tRPC equivalent

<task type="auto">
  <name>Task 2: Produce migration roadmap</name>
  <files>
    - .planning/phases/121-settings-unification/REST-TRPC-ASSESSMENT.md
  </files>
  <action>
Based on the audit, produce a 3-phase migration roadmap with effort estimates.

**Phase A — Feature parity (1-2 days):**

- Add missing guarantees to the canonical surface for duplicated operations
- Options: (a) add rate limiting to tRPC upsert, OR (b) add assist scope to tRPC upsert
- Add `revalidateTag(CACHE_TAGS.SETTINGS)` to tRPC settings router (currently only `revalidateAdminChanges`)
- Determine: which surface is the canonical one?

**Phase B — Surface consolidation (2-3 days):**

- Pick one surface as canonical for settings operations
- Option 1: REST canonical → move tRPC procedures to REST, deprecate tRPC settings router
- Option 2: tRPC canonical → move page-flags/services-config/provider-reg-mode to tRPC
- Mark deprecated surface with `@deprecated` JSDoc + migration guide in comments

**Phase C — Cleanup (1 day):**

- Remove deprecated surface
- Update all consumers
- Remove migration comments

**Recommendation:** Option 1 (REST canonical) is pragmatic because:

- Page-flags, services-config, and provider-reg-mode are already REST-only
- Admin UI already calls REST endpoints directly
- REST endpoints have rate limiting and assist scope guards (tRPC doesn't)
- tRPC settings router has only 1 consumer (OpenAPI docs) aside from tests
- Migration: move `listSettings`/`deleteSetting` to REST, deprecate tRPC router

OR

**Recommendation:** Option 2 (tRPC canonical) if:

- The team is standardizing on tRPC for all internal APIs
- The OpenAPI generation from tRPC is a strategic requirement
- Then: move page-flags/services-config/provider-reg-mode to tRPC procedures
