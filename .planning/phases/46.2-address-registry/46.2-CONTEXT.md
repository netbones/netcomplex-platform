<domain>
## Phase Boundary

Build the **Platform Address Registry** — the canonical, single-source-of-truth namespace for all addresses within a NetComplex tenant. Currently addresses are scattered across 5 tables (`StandardSeat`, `SoloSeat`, `PremiumSeat`, `Profile`, `Property`) with no cross-table uniqueness enforcement. The Address Registry becomes a first-class domain entity alongside `User`, `Tenant`, and `Conversation`, consumed by every other model.

### What this phase delivers

1. **`Address` model** — Central registry table with unique `address` per tenant, `kind` (STANDARD, ALIAS, SOLO, PREMIUM, PROVIDER, SYSTEM), `status` (ACTIVE, RESERVED, COOLING_OFF, ARCHIVED, DELETED), `ownerType`/`ownerId` polymorphic owner reference, `canonicalAddressId` for aliases, `forwardStrategy` (DIRECT, HOUSEHOLD)
2. **`Handle` model** — Tenant-scoped short handles for `@mention` resolution in chat (maps `@john` → address record), separate from the canonical address
3. **`AddressEndpoint` model** — Transport decoupling (INTERNAL_CHAT, EMAIL, WEBFORM, API, SMS, etc.) so address resolution is independent of how messages arrive
4. **Address lifecycle states** — Cooling-off (6 months), archival (90 days), portability window (30 days) enforced at the database level
5. **Cross-table uniqueness** — Single `@unique` constraint on `Address.address` replaces the current per-table uniqueness that allows collisions across seat types
6. **Migration path** — Populate from existing seat tables, add `addressId` foreign keys, keep legacy `platformAddress` columns as cached/denormalized values

### What this phase does NOT deliver

- Rewriting the chat/messaging system to use address-based routing (enables it, does not implement)
- Full migration of existing mentions/messages to address IDs
- Federation between NetComplex instances
- External email gateway (transport adapters enabled, not built)
- Admin UI for address management (schema + service layer only)
  </domain>

<decisions>
## Implementation Decisions

### Architecture (Locked — from COMMUNIQUE-02 Response)

- **Central Address Registry** (Option A++) — Single `Address` table as source of truth, all other tables reference it via `addressId` FK
- **Handle separate from Address** — `Handle` table for `@mention` resolution (short, friendly, tenant-scoped), `Address` table for canonical identity
- **Transport decoupling** — `AddressEndpoint` table so an address can receive messages via INTERNAL_CHAT, EMAIL, WEBFORM, API, etc. without changing the address model
- **Polymorphic owner** — `ownerType` + `ownerId` pattern (no FK constraint) for Address ownership
- **3-phase migration** — Phase 1: Create + Populate + FK references (legacy columns kept). Phase 2: Read through AddressService only. Phase 3: Remove legacy columns

### Schema Design (Locked)

```
Address
------
id              String   @id
tenantId        String
address         String   @unique   // "john@soralia.org"
localPart       String             // "john"
domain          String             // "soralia.org"
kind            AddressKind        // STANDARD | ALIAS | SOLO | PREMIUM | PROVIDER | SYSTEM
status          AddressStatus      // ACTIVE | RESERVED | COOLING_OFF | ARCHIVED | DELETED
ownerType       AddressOwnerType?  // STANDARD_SEAT | PROFILE | SOLO_SEAT | PREMIUM_SEAT | PROVIDER | SYSTEM
ownerId         String?
canonicalAddressId String?        // for aliases pointing to primary address
forwardStrategy ForwardStrategy?  // DIRECT | HOUSEHOLD
receiveExternal Boolean  @default(false)
coolingUntil    DateTime?
archivedUntil   DateTime?
releasedAt      DateTime?
createdAt       DateTime
updatedAt       DateTime

Handle
------
id              String   @id
tenantId        String
handle          String             // "john", "maintenance", "admin"
addressId       String             // FK → Address
status          HandleStatus       // ACTIVE | RESERVED | RELEASED
createdAt       DateTime

AddressEndpoint
--------------
id              String   @id
addressId       String             // FK → Address
type            EndpointType       // INTERNAL_CHAT | EMAIL | WEBFORM | API | SMS | WHATSAPP | PUSH
enabled         Boolean  @default(true)
config          Json?
createdAt       DateTime
```

### Existing Tables — FK Additions

```
StandardSeat    → addressId FK → Address
SoloSeat        → addressId FK → Address
PremiumSeat     → addressId FK → Address
Profile         → aliasAddressId FK → Address (replaces profileAddress)
Property        → addressId FK → Address (replaces platformAddress)
ServiceProvider → addressId FK → Address
```

### Migration Strategy (Locked)

- **Phase 1 (this phase):** Create Address/Handle/AddressEndpoint tables + populate from existing records + add `addressId` FKs to seat tables. Keep legacy `platformAddress`/`profileAddress` columns as cached values
- **Phase 2 (future):** All reads go through AddressService. Legacy columns become denormalized cache
- **Phase 3 (future):** Remove direct ownership of address strings from seat tables

### Service Layer

- `AddressService` with methods: `reserve()`, `release()`, `resolve()`, `move()`, `forward()`, `archive()`, `lookup()`, `validate()`, `generate()`
- `HandleService` with methods: `search()`, `register()`, `release()`, `resolve()`
- All modules depend on these services instead of touching seat tables directly

- Error handling patterns for the service layer

- Whether to use Drizzle or Prisma for the service layer queries

## Specific Requirements from COMMUNIQUE-02

### Address Lifecycle Rules (from SaaS Agreement)

| Event              | Duration  | Rule                                                           |
| ------------------ | --------- | -------------------------------------------------------------- |
| Portability Window | 30 days   | Departing Premium Seat can export data                         |
| Archival Period    | 90 days   | Read-only retention before permanent deletion                  |
| Cooling-Off Period | 6 months  | Premium Seat address cannot be reissued                        |
| Household turnover | Immediate | New occupant moves in — alias addresses reassign?              |
| Liberation         | Per event | John upgrades from alias `john.unit042` to solo `john@soralia` |

### Reserved Platform Names

admin, support, system, billing, help, maintenance, security, office, community, events

### Address Format Conventions

| Entity        | Address Pattern            |
| ------------- | -------------------------- |
| Standard Seat | `unitNNN@soralia.org`      |
| Address Alias | `name.unitNNN@soralia.org` |
| Solo Seat     | `name@soralia.org`         |
| Premium Seat  | `custom@soralia.org`       |
| Provider      | `company@soralia.org`      |

</specifics>
