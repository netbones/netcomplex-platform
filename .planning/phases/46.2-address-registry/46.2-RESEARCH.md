# Phase 46.2: Platform Address Registry — Research

**Researched:** 2026-06-30
**Domain:** Multi-tenant address/identity namespace (schema, migrations, service layer)
**Confidence:** HIGH

## Summary

Phase 46.2 introduces a canonical Address Registry as a first-class domain entity, replacing the current 5-table address scatter (`StandardSeat.platformAddress`, `SoloSeat.platformAddress`, `PremiumSeat.platformAddress`, `Profile.profileAddress`, `Property.platformAddress`). The current architecture has no cross-table uniqueness — `assertAddressUnique()` in `src/shared/api/db.ts:352-376` is a manual guard that only checks 3 of the 5 tables.

The project uses a dual-ORM stack (Prisma for migrations, Drizzle for queries via `@api/server`). Prisma generates Drizzle schema files in `src/db/schema/` via `prisma-generator-drizzle`. All new models must follow established patterns: Prisma enums at the bottom of `schema.prisma` with `SCREAMING_SNAKE_CASE`, Drizzle tables in `src/db/schema/<kebab>.ts`, Drizzle enums in separate files, and registration in the `dbSchema` object and `@api/server` barrel exports.

The recommended service layer pattern is a class-based service (matching `PayPalService` / `PaystackService` in `src/server/payments/`) instantiated with a Drizzle transaction for testability. The migration should use a `YYYYMMDDhhmmss` timestamped directory with idempotent SQL (guarded `CREATE TYPE`, `ADD VALUE IF NOT EXISTS`).

**Primary recommendation:** Build the Address/Handle/AddressEndpoint schema first (Prisma + Drizzle), then a class-based `AddressService`, then the migration to backfill from 5 existing tables. Keep legacy `platformAddress` columns as cached denormalized values (Phase 1 of 3-phase migration).

### Table Convention (Drizzle)

Existing pattern from `PremiumSeat` (`src/db/schema/premium-seats.ts`):

```typescript
import { pgTable, text, boolean, integer, timestamp } from 'drizzle-orm/pg-core';
import { seatStatusEnum } from './seat-status-enum';

export const premiumSeats = pgTable('PremiumSeat', {
  id: text('id').primaryKey(),
  tenantId: text('tenantId').notNull(),
  userId: text('userId').notNull(),
  isActive: boolean('isActive').default(true).notNull(),
  portfolioName: text('portfolioName'),
  subscriptionTier: text('subscriptionTier').default('basic').notNull(),
  maxProperties: integer('maxProperties').default(5).notNull(),
  platformAddress: text('platformAddress').notNull(),
  organizationId: text('organizationId'),
  status: seatStatusEnum('status').default('ACTIVE').notNull(),
  archivedAt: timestamp('archivedAt', { mode: 'date', precision: 3 }),
  createdAt: timestamp('createdAt', { mode: 'date', precision: 3 }).defaultNow().notNull(),
  updatedAt: timestamp('updatedAt', { mode: 'date', precision: 3 }).defaultNow().notNull(),
  messageRetentionDays: integer('messageRetentionDays').default(30).notNull(),
  tier: text('tier').default('foundation').notNull(),
});
```

Key conventions:

- `text('id').primaryKey()` — no `@default(cuid())` in Drizzle (Prisma handles defaults)
- `text('fieldName')` — camelCase field to PascalCase column mapping
- `timestamp('fieldName', { mode: 'date', precision: 3 })` — for DateTime columns
- `dateEnum('fieldName').default('VALUE').notNull()` — for enums
- `Json?` in Prisma maps to `jsonb('fieldName')` in Drizzle

### Tenant Isolation Pattern

The canonical compound unique pattern in this project is:

```prisma
model Setting {
  // ...
  tenantId  String
  key       String
  // ...
  @@unique([tenantId, key])
}
```

This also appears in:

- `TenantModule`: `@@unique([tenantId, moduleKey])`
- `Profile`: `@@unique([householdId, profileAddress])`
- `ConversationParticipant`: `@@unique([conversationId, userId])`
- `UserAchievement`: `@@unique([tenantId, userId, achievementId])`
- `TenantAiUsage`: `@@unique([tenantId, billingMonth])`

**For Address:** Use `@@unique([tenantId, address])` to scope uniqueness per tenant, enabling the same address string across different tenants.

### Timestamp Conventions

All models follow this pattern:

### Polymorphic Owner Pattern

The locked decision uses `ownerType` + `ownerId` with no FK constraint (different from any existing pattern in the codebase — no existing model uses polymorphic references). This is correct for the use case since the owner can be any of 6 different entity types across 6 different tables.

**Important constraint:** There is no FK on `ownerId` because a single FK cannot reference multiple parent tables. The service layer must validate `ownerType`/`ownerId` at application level.

## Migration Patterns

### Format: Timestamped directory

Migrations use the format `YYYYMMDDHHmmss_description/migration.sql`. Example: `20260624000000_add_user_role_and_seat_lifecycle/`.

### Idempotent SQL

The project uses guarded SQL for idempotency:

**Enum creation** (from `20260624000000_add_user_role_and_seat_lifecycle/migration.sql`):

```sql
-- Add a value to an existing enum
ALTER TYPE "Role" ADD VALUE IF NOT EXISTS 'USER' BEFORE 'RESIDENT';

-- Create a new enum type (idempotent)
DO $$ BEGIN
  CREATE TYPE "SeatStatus" AS ENUM ('ACTIVE', 'ARCHIVED', 'COOLING_OFF');
EXCEPTION WHEN duplicate_object THEN NULL;
END $$;
```

**Column additions:**

```sql
ALTER TABLE "StandardSeat" ADD COLUMN "status" "SeatStatus" NOT NULL DEFAULT 'ACTIVE';
ALTER TABLE "StandardSeat" ADD COLUMN "archivedAt" TIMESTAMP(3);
```

### Migration File for Phase 46.2

Recommended structure (e.g., `20260630120000_add_address_registry/migration.sql`):

```sql
-- Phase 46.2: Platform Address Registry — Core schema
-- Creates Address, Handle, AddressEndpoint tables + adds addressId FKs to 6 existing tables

-- 1. Create enum types
DO $$ BEGIN CREATE TYPE "AddressKind" AS ENUM ('STANDARD','ALIAS','SOLO','PREMIUM','PROVIDER','SYSTEM'); EXCEPTION WHEN duplicate_object THEN NULL; END $$;
DO $$ BEGIN CREATE TYPE "AddressStatus" AS ENUM ('ACTIVE','RESERVED','COOLING_OFF','ARCHIVED','DELETED'); EXCEPTION WHEN duplicate_object THEN NULL; END $$;
DO $$ BEGIN CREATE TYPE "AddressOwnerType" AS ENUM ('STANDARD_SEAT','PROFILE','SOLO_SEAT','PREMIUM_SEAT','PROVIDER','SYSTEM'); EXCEPTION WHEN duplicate_object THEN NULL; END $$;
DO $$ BEGIN CREATE TYPE "ForwardStrategy" AS ENUM ('DIRECT','HOUSEHOLD'); EXCEPTION WHEN duplicate_object THEN NULL; END $$;
DO $$ BEGIN CREATE TYPE "HandleStatus" AS ENUM ('ACTIVE','RESERVED','RELEASED'); EXCEPTION WHEN duplicate_object THEN NULL; END $$;
DO $$ BEGIN CREATE TYPE "EndpointType" AS ENUM ('INTERNAL_CHAT','EMAIL','WEBFORM','API','SMS','WHATSAPP','PUSH'); EXCEPTION WHEN duplicate_object THEN NULL; END $$;

-- 2. Create Address table
CREATE TABLE "Address" (
  "id" TEXT PRIMARY KEY,
  "tenantId" TEXT NOT NULL,
  "address" TEXT NOT NULL,
  "localPart" TEXT NOT NULL,
  "domain" TEXT NOT NULL,
  "kind" "AddressKind" NOT NULL,
  "status" "AddressStatus" NOT NULL DEFAULT 'ACTIVE',
  "ownerType" "AddressOwnerType",
  "ownerId" TEXT,
  "canonicalAddressId" TEXT,
  "forwardStrategy" "ForwardStrategy",
  "receiveExternal" BOOLEAN NOT NULL DEFAULT false,
  "coolingUntil" TIMESTAMP(3),
  "archivedUntil" TIMESTAMP(3),
  "releasedAt" TIMESTAMP(3),
  "createdAt" TIMESTAMP(3) NOT NULL DEFAULT NOW(),
  "updatedAt" TIMESTAMP(3) NOT NULL DEFAULT NOW(),
  CONSTRAINT "Address_tenantId_address_key" UNIQUE ("tenantId", "address")
);

-- 3. Create Handle table
CREATE TABLE "Handle" (
  "id" TEXT PRIMARY KEY,
  "tenantId" TEXT NOT NULL,
  "handle" TEXT NOT NULL,
  "addressId" TEXT NOT NULL,
  "status" "HandleStatus" NOT NULL DEFAULT 'ACTIVE',
  "createdAt" TIMESTAMP(3) NOT NULL DEFAULT NOW(),
  CONSTRAINT "Handle_tenantId_handle_key" UNIQUE ("tenantId", "handle"),
  CONSTRAINT "Handle_addressId_fkey" FOREIGN KEY ("addressId") REFERENCES "Address"("id") ON DELETE CASCADE
);

-- 4. Create AddressEndpoint table
CREATE TABLE "AddressEndpoint" (
  "id" TEXT PRIMARY KEY,
  "addressId" TEXT NOT NULL,
  "type" "EndpointType" NOT NULL,
  "enabled" BOOLEAN NOT NULL DEFAULT true,
  "config" JSONB,
  "createdAt" TIMESTAMP(3) NOT NULL DEFAULT NOW(),
  CONSTRAINT "AddressEndpoint_addressId_fkey" FOREIGN KEY ("addressId") REFERENCES "Address"("id") ON DELETE CASCADE

-- 5. Add addressId FKs to existing tables (nullable)
ALTER TABLE "StandardSeat" ADD COLUMN "addressId" TEXT;
ALTER TABLE "SoloSeat" ADD COLUMN "addressId" TEXT;
ALTER TABLE "PremiumSeat" ADD COLUMN "addressId" TEXT;
ALTER TABLE "Profile" ADD COLUMN "aliasAddressId" TEXT;
ALTER TABLE "Property" ADD COLUMN "addressId" TEXT;
ALTER TABLE "ServiceProvider" ADD COLUMN "addressId" TEXT;

-- 6. Add FK constraints
ALTER TABLE "StandardSeat" ADD CONSTRAINT "StandardSeat_addressId_fkey" FOREIGN KEY ("addressId") REFERENCES "Address"("id");
ALTER TABLE "SoloSeat" ADD CONSTRAINT "SoloSeat_addressId_fkey" FOREIGN KEY ("addressId") REFERENCES "Address"("id");
ALTER TABLE "PremiumSeat" ADD CONSTRAINT "PremiumSeat_addressId_fkey" FOREIGN KEY ("addressId") REFERENCES "Address"("id");
ALTER TABLE "Profile" ADD CONSTRAINT "Profile_aliasAddressId_fkey" FOREIGN KEY ("aliasAddressId") REFERENCES "Address"("id");
ALTER TABLE "Property" ADD CONSTRAINT "Property_addressId_fkey" FOREIGN KEY ("addressId") REFERENCES "Address"("id");
ALTER TABLE "ServiceProvider" ADD CONSTRAINT "ServiceProvider_addressId_fkey" FOREIGN KEY ("addressId") REFERENCES "Address"("id");

-- 7. Backfill Address table from existing data
INSERT INTO "Address" ("id", "tenantId", "address", "localPart", "domain", "kind", "status", "ownerType", "ownerId", "createdAt", "updatedAt")
SELECT
  gen_random_uuid()::TEXT,
  "tenantId",
  "platformAddress",
  split_part("platformAddress", '@', 1),
  split_part("platformAddress", '@', 2),
  'STANDARD'::"AddressKind",
  CASE WHEN "status" = 'ARCHIVED' THEN 'ARCHIVED'::"AddressStatus" ELSE 'ACTIVE'::"AddressStatus" END,
  'STANDARD_SEAT'::"AddressOwnerType",
  "id",
  "createdAt",
  "updatedAt"
FROM "StandardSeat"
WHERE "platformAddress" IS NOT NULL
ON CONFLICT ("tenantId", "address") DO NOTHING;

-- Repeat for SoloSeat (kind=SOLO, ownerType=SOLO_SEAT)
-- Repeat for PremiumSeat (kind=PREMIUM, ownerType=PREMIUM_SEAT)
-- Repeat for Profile (kind=ALIAS, ownerType=PROFILE, on profileAddress)
-- Repeat for Property (kind=STANDARD, ownerType=SYSTEM on platformAddress)

-- 8. Update FK columns on existing tables (link back to Address)

-- 9. Create indexes
CREATE INDEX "Address_tenantId_idx" ON "Address"("tenantId");
CREATE INDEX "Address_ownerType_ownerId_idx" ON "Address"("ownerType", "ownerId");
CREATE INDEX "Address_status_idx" ON "Address"("status");
CREATE INDEX "Handle_addressId_idx" ON "Handle"("addressId");
CREATE INDEX "AddressEndpoint_addressId_idx" ON "AddressEndpoint"("addressId");
```

### Backfill Strategy

The backfill (step 7 above) populates the Address table from:

1. `StandardSeat.platformAddress` → `kind: STANDARD`, `ownerType: STANDARD_SEAT`
2. `SoloSeat.platformAddress` → `kind: SOLO`, `ownerType: SOLO_SEAT`
3. `PremiumSeat.platformAddress` → `kind: PREMIUM`, `ownerType: PREMIUM_SEAT`
4. `Profile.profileAddress` → `kind: ALIAS`, `ownerType: PROFILE`
5. `Property.platformAddress` → `kind: STANDARD`, `ownerType: SYSTEM` (Property is not a seat)
6. `ServiceProvider.email` → `kind: PROVIDER`, `ownerType: PROVIDER` (generate address from email)

After populating Address, back-update the `addressId` FKs on each source table via `UPDATE ... FROM "Address" WHERE ...`.

## Don't Hand-Roll

| Problem                          | Don't Build                                              | Use Instead                                                                       | Why                                                                                                 |
| -------------------------------- | -------------------------------------------------------- | --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Address uniqueness across tables | Application-level uniqueness check that queries 6 tables | `@@unique([tenantId, address])` at DB level + `INSERT ... ON CONFLICT DO NOTHING` | Race conditions between check and insert; DB constraint is atomic                                   |
| Address format parsing           | Custom regex per address type                            | Store `localPart`/`domain` pre-parsed in the Address row                          | Parsing once at write time is cheaper than parsing on every read; domain changes are extremely rare |
| Tenant isolation                 | `WHERE tenantId = ?` in every query                      | `@@unique([tenantId, address])` + `eq(addresses.tenantId, tenantId)` in Drizzle   | Belt-and-suspenders: DB constraint + query filter                                                   |
| ID generation                    | Sequential IDs or ULIDs                                  | `crypto.randomUUID()` (JavaScript)                                                | All existing models use random UUIDs; consistent with the codebase                                  |
| Timestamp management             | Manual `new Date()`                                      | `@default(now())` / `@updatedAt` in Prisma, `defaultNow()` in Drizzle             | Consistent across all models; timezone-safe                                                         |

**Key insight:** The `assertAddressUnique` function in `db.ts:356-376` is NOT needed for the Address table itself (the unique constraint handles it). It should be UPDATED to check the Address table instead of the 3 seat tables, since the Address table is now the source of truth.

## Common Pitfalls

### Pitfall 1: Forgetting to register in all 4 places

**What goes wrong:** New Drizzle table works in migration but queries fail at runtime because the table isn't in `dbSchema`.
**Why it happens:** The project requires manual registration in `db.ts` (import + dbSchema object + export block) and `server/index.ts` (export).
**How to avoid:** Use a checklist for each new table: (1) Drizzle schema file, (2) relations file, (3) `db.ts` import, (4) `db.ts` dbSchema entry, (5) `db.ts` export, (6) `server/index.ts` export.
**Warning signs:** Runtime error `relation "Address" does not exist` despite migration running successfully — the Drizzle schema wasn't registered.

### Pitfall 2: `@@unique([tenantId, address])` vs `@unique` on address alone

**What goes wrong:** Using `@unique` on `address` without `tenantId` means address strings can't be reused across tenants (e.g., `admin@soralia.org` in tenant A blocks `admin@oakwood.org` in tenant B).
**Why it happens:** Forgetting that this is a multi-tenant platform. Every tenant must have its own address namespace.
**How to avoid:** Always use `@@unique([tenantId, address])`. Reference the `Setting` model as the canonical example.

### Pitfall 3: Prisma-Drizzle enum drift

**What goes wrong:** Adding an enum value to Prisma but forgetting the corresponding Drizzle enum file.
**Why it happens:** The `prisma-generator-drizzle` auto-generates schemas but enum files are often manually maintained.
**How to avoid:** After every Prisma schema change, run `npx prisma generate` and verify the generated Drizzle files in `src/db/schema/`. If enum values changed, update the manual enum file.
**Warning signs:** TypeScript errors about invalid enum values in Drizzle queries — the Drizzle enum doesn't match the database.

### Pitfall 4: Backfill race with active writes

**What goes wrong:** Migration backfill runs while the application is inserting new records into seat tables, causing missed addresses.
**Why it happens:** Deployment without a maintenance window or write-lock during migration.
**How to avoid:** Use `INSERT ... ON CONFLICT DO NOTHING` in the migration SQL so duplicate inserts are harmless. Run a second backfill pass after deployment to catch any records inserted during the migration window.

### Pitfall 5: `ownerType` / `ownerId` validation gap

**What goes wrong:** An `ownerType` of `STANDARD_SEAT` paired with an `ownerId` that points to a `SoloSeat` — no FK constraint catches this.
**Why it happens:** Polymorphic patterns cannot use database-level FK constraints because a single column cannot reference multiple parent tables.
**How to avoid:** The `AddressService.reserve()` method must validate the `ownerType`/`ownerId` pair exists in the correct table before inserting. Add an integration test for each owner type.

## Risks & Mitigations

### Risk 1: Silent address collisions during backfill

**Severity:** HIGH
**Description:** If two seat tables have the same `platformAddress` string, the `ON CONFLICT DO NOTHING` will silently drop one. The dropped address won't have an Address record.
**Mitigation:** Before backfill, run a detection query:

```sql
SELECT 'DUPLICATE' as issue, platformAddress, array_agg(DISTINCT source) as sources
FROM (
  SELECT platformAddress, 'StandardSeat' as source FROM "StandardSeat"
  UNION ALL SELECT platformAddress, 'SoloSeat' FROM "SoloSeat"
  UNION ALL SELECT platformAddress, 'PremiumSeat' FROM "PremiumSeat"
  UNION ALL SELECT "profileAddress", 'Profile' FROM "Profile"
  UNION ALL SELECT platformAddress, 'Property' FROM "Property"
) t
GROUP BY platformAddress HAVING COUNT(*) > 1;
```

If duplicates exist, decide merge strategy before migration.

### Risk 2: Orphan addressId FKs after backfill

**Severity:** MEDIUM
**Description:** If the backfill INSERT succeeds but the subsequent UPDATE to set `addressId` on existing tables fails mid-way, some records will have no `addressId`.
**Mitigation:** Run migration in a transaction (Prisma migrations are transactional by default). Add a verification query after migration:

```sql
SELECT 'StandardSeat' as tbl, COUNT(*) as missing_fk
FROM "StandardSeat" WHERE "addressId" IS NULL AND "platformAddress" IS NOT NULL
UNION ALL SELECT 'SoloSeat', COUNT(*) FROM "SoloSeat" WHERE "addressId" IS NULL AND "platformAddress" IS NOT NULL
-- ... repeat for each table
```

### Risk 3: ServiceProvider address generation from email

**Severity:** LOW
**Description:** ServiceProvider has `email` but no `platformAddress`. An address must be generated (e.g., `company@soralia.org` from email `contact@company.com`).
**Mitigation:** Derive `localPart` from `companyName` (slugified), not email. Email format varies widely; company name is more stable:

```sql
INSERT INTO "Address" (...)
SELECT
  gen_random_uuid()::TEXT,
  sp."tenantId",
  lower(regexp_replace(sp."companyName", '[^a-zA-Z0-9]', '', 'g')) || '@soralia.org',
  -- ...
FROM "ServiceProvider" sp
WHERE sp."email" IS NOT NULL;
```

### Risk 4: `Profile.profileAddress` has `@@unique([householdId, profileAddress])`

**Severity:** MEDIUM
**Description:** The Profile model has `@@unique([householdId, profileAddress])` — per-household uniqueness, not global. This means the same `profileAddress` CAN exist across different households, which violates the Address table's `@@unique([tenantId, address])`.
**Mitigation:** Pre-migration detection query (as in Risk 1). If duplicates exist across households, generate unique addresses (e.g., append household ID suffix) for conflicting records.

## Open Questions

1. **Where should AddressService and HandleService live?**
   - What we know: Existing class-based services live in `src/server/payments/`. No `src/server/services/` directory exists. `@api/server` is the canonical barrel for server-side imports.
   - What's unclear: Whether new domain services should follow the payments pattern (`src/server/services/`) or live in `src/shared/api/` for direct export from `@api/server`.
   - Recommendation: Place in `src/shared/api/` with `'use server'` or `import 'server-only'` — this keeps them co-located with existing API infrastructure and exportable from `@api/server`. Use `src/shared/api/address-service.ts` and `src/shared/api/handle-service.ts`.

2. **Should the service layer use Prisma Client or Drizzle?**
   - What we know: All existing route handlers and tRPC procedures use Drizzle via `@api/server`. Prisma Client is only used for migrations and `prisma generate`.
   - What's unclear: Whether `AddressService` should use the same Drizzle-centric approach or leverage Prisma's type-safe client for the new models.
   - Recommendation: Use Drizzle exclusively — it's the project standard for runtime queries, edge-compatible, and consistent with every other service in the codebase.

3. **How to handle `Property.platformAddress` backfill?**
   - What we know: Properties are not address owners (they're physical locations). `platformAddress` on Property is `unit042@soralia.org` format — same as StandardSeat.
   - What's unclear: Whether Property addresses should be `kind: STANDARD` with `ownerType: SYSTEM`, or whether they should be linked to the property's StandardSeat.
   - Recommendation: Property addresses get `kind: STANDARD`, `ownerType: SYSTEM`, `ownerId: property.id`. The Property → Address link is direct (not through a seat). If a Property's address collides with a StandardSeat's address (they should be the same), the `ON CONFLICT DO NOTHING` will silently merge them.
