## 1. System Classification

**System Type:** Structured Data Extraction / Advisory Response

**Description:**
The AI intake screen analyzes dispute descriptions to help residents self-assess whether their dispute warrants formal filing. A sanitized description is sent to the AI provider pool (Phase 104) and returns a structured advisory assessment (toneScore, likelyFrivolous, suggestedCategory, deEscalationTip). The response is advisory only — never persisted, never binding. Users are residents, committee members, and board members filing disputes in a community management platform (Netcomplex/Soralia Village). "Good" means the AI returns valid JSON with all four fields populated, the frivolity signal is directionally useful (not perfect), and the de-escalation tip is constructive. The system degrades gracefully — when AI is unavailable, the intake wizard skips the step entirely.

**Critical Failure Modes:**

1. PII leakage — description sent to AI provider containing unsanitized personal data (POPIA violation)
2. Invalid JSON response — AI returns malformed JSON causing intake screen to crash or hang
3. De-escalation sabotage — AI generates inflammatory or accusatory language in the deEscalationTip
4. Quota exhaustion — intake screen consumes Phase 104 AI quota needed for other modules

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Community Governance / HOA Management (Residential Community Schemes — South Africa)

**User Population:** Residents (180-home Soralia Village anchor tenant), HOA committee members, board members, and platform administrators of a multi-tenant community management SaaS platform (Netcomplex). Users file disputes in a shared living context — neighbour-to-neighbour conflicts, resident-to-HOA grievances, and HOA-to-resident compliance issues. The AI intake screen is an advisory-only pre-submission gate; the response is never persisted and never binding.

**Stakes Level:** High

**Output Consequence:** The AI produces a structured advisory assessment (toneScore, likelyFrivolous, suggestedCategory, deEscalationTip). Residents use this to self-assess whether to proceed with formal filing. A false negative on `likelyFrivolous` (labeling a legitimate grievance as frivolous) could discourage a resident from filing a valid dispute — potentially denying them access to the internal resolution mechanism that South African law (CSOS Act) mandates must be available. A false positive (passing through a genuinely frivolous filing) wastes moderator time. The deEscalationTip, if accusatory or inflammatory, could escalate community tensions between neighbours who must continue cohabiting. Critically, if PII (surnames, unit numbers) leaks through the AI provider call, it constitutes a POPIA breach — the dispute description, even sanitised, is classified HIGH SENSITIVITY per ADVISORY-017.

### What Domain Experts Evaluate Against

**Dimension: Frivolity classification consistency**
Good (domain expert would accept): The `likelyFrivolous` flag correctly identifies descriptions that lack an actionable grievance — no specific rule, by-law, damage, dates, or obligation is cited. For example, "My neighbour is annoying and I don't like their car" → `likelyFrivolous: true`. Legitimate disputes like "The neighbour's dog has barked every night after 22:00 since 12 June, violating Rule 4.2 of the Conduct Rules" → `likelyFrivolous: false`.
Bad (domain expert would flag): The model flags "I want to file a complaint but I don't know which rule applies" as frivolous — a valid grievance stated without legal language is still valid. Conversely, the model passes through "They're always doing things to upset me" without any specificity.
Stakes: Critical
Source: CSOS Act Section 38 — internal dispute resolution must be accessible. SAIA 2019 benchmark: cooling-off periods reduce frivolous filings by ~40%; classification errors that discourage legitimate filing undermine the HOA's CSOS compliance obligation.

**Dimension: Category suggestion accuracy**
Good (domain expert would accept): The `suggestedCategory` aligns with the CSOS-recognisable dispute taxonomy in the community scheme context. "Barking dog after hours" → PETS. "Visitor parked in my allocated bay" → PARKING. "Body corporate hasn't repaired the leaking roof despite three maintenance requests" → COMMON_PROPERTY. "Levy was increased without a special general meeting vote" → GOVERNANCE.
Bad (domain expert would flag): Category mismatch that would confuse a CSOS adjudicator reviewing the internal resolution record. "Leaking roof in common area" → DAMAGE (it's COMMON_PROPERTY — the HOA is liable, not a specific resident). Cross-category misclassification between RULE_ENFORCEMENT and CONDUCT (the distinction matters for which by-law provision applies).
Stakes: High
Source: Community Schemes Ombud Service Act Regulations GN R607 of 2016, Regulation 4 — applications require categorisation matching CSOS taxonomy. Miscategorisation in the intake layer could misdirect the complainant before a moderator reviews the case.

**Dimension: De-escalation quality — tone and constructiveness**
Good (domain expert would accept): The deEscalationTip is a single sentence that reframes the conflict constructively. It focuses on specific dates, behaviours, and applicable rules rather than emotional states. For a high-tone description about a neighbour conflict: "It sounds like this has been stressful. To build the strongest case, focus on specific dates, specific behaviours you observed, and the community rule that applies — facts are what moderators can act on." For disputes about HOA governance: "Request a copy of the specific by-law or board resolution in writing first — it may not say what you expect, and having it documented strengthens your case."
Bad (domain expert would flag): Inflammatory, accusatory, or dismissive language. "You seem very angry — you should calm down before filing." (patronising). "These complaints rarely succeed — are you sure you want to proceed?" (discouraging). Any suggestion that takes sides or implies the respondent is at fault (the AI must remain neutral). Generic tips like "Try talking to your neighbour" when the description already states they have tried and been met with hostility (context-blind de-escalation).
Stakes: Critical
Source: Community mediation best practice (SAIA 2019 benchmark). Disputes in residential community schemes are between neighbours who must continue cohabiting; inflammatory intake responses risk escalating interpersonal conflict. Multi-language context (South Africa — the community may include isiXhosa, isiZulu, and Afrikaans speakers where tone translation is especially delicate).

**Dimension: PII sanitisation completeness**
Good (domain expert would accept): The sanitised description sent to the AI provider contains no surnames, unit numbers, street addresses, phone numbers, email addresses, ID numbers, or vehicle registration plates. A description reading "John Smith in Unit 12 has been..." arrives at the AI as "A neighbour has been...". Names like "Mr. van der Merwe" and "Thabo" are stripped or replaced with role-descriptors.
Bad (domain expert would flag): Partial sanitisation — surnames are stripped but unit numbers remain ("Unit 12" identifies a specific household in a 180-home scheme). Vehicle registration plates pass through ("CA 123-456 parks in my bay" — the plate uniquely identifies an individual in South Africa per POPIA Section 1 definition of personal information). Indirect identifiers survive that, combined with community knowledge, could re-identify individuals.
Stakes: Critical
Source: POPIA Section 19 (security measures on integrity and confidentiality), Section 72 (cross-border transfer — AI providers Anthropic/OpenAI are US-based). ADVISORY-017 classifies dispute descriptions as HIGH SENSITIVITY. The `sanitizeDescriptionForAi()` utility is the single choke point — failure here is a reportable POPIA breach.

**Dimension: Graceful degradation behaviour**
Good (domain expert would accept): When the AI provider is unavailable (NullProvider returned, quota exhausted, API error), the route returns 503 with a message that the user may proceed without screening. The intake wizard (Phase 107 frontend) collapses from 4 stages to 3 with zero user-visible error indication — the frivolity step is silently excluded. Safe defaults (toneScore: 0, likelyFrivolous: false, suggestedCategory: OTHER, deEscalationTip: null) are returned when JSON parsing fails — the user is never blocked.
Bad (domain expert would flag): The route returns a 5xx error that blocks the intake wizard entirely — a frustrated resident cannot file a dispute because the advisory AI step failed. The route retries the AI call multiple times before returning, creating a 15-second spinner while the resident waits. The route returns safe defaults but does not log the failure, making degradation invisible to operations.
Stakes: High
Source: ADVISORY-017 §7 (intake wizard design — "never blocking") and §10 (API route spec for intake-screen). CSOS Act Section 38 access-to-justice principle — no technical failure of an advisory tool should impede the formal dispute resolution pathway.

### Known Failure Modes in This Domain

1. **PII leakage through AI provider call (POPIA cross-border transfer violation).** Dispute descriptions routinely contain surnames, unit numbers, and vehicle registrations. If the `sanitizeDescriptionForAi()` step is skipped or incomplete, personally identifiable information is transmitted to US-based LLM providers (Anthropic, OpenAI). Under POPIA Section 72, cross-border transfer of personal information requires either adequate safeguards, data subject consent, or contractual necessity. This intake screen is advisory — consent is implied by use but not explicit. Mitigation: server-side sanitisation is the single choke point; add a pre-commit hook that flags any `provider.complete()` call not preceded by the sanitise utility.

2. **AI misclassification discouraging legitimate CSOS-path filings.** A resident with a valid governance or levy dispute receives `likelyFrivolous: true` and the message "Your description may be hard for a moderator to act on." They abandon filing. The HOA later claims internal resolution was "available" but the AI intake gate functionally discouraged it — a CSOS adjudicator could find the internal mechanism was not genuinely accessible. Mitigation: the AI output is advisory only; the wizard always shows a "Continue anyway" button regardless of `likelyFrivolous` value.

3. **De-escalation tip causing interpersonal escalation in a closed community.** In a 180-home scheme, neighbours know each other. An AI-generated de-escalation tip that inadvertently characterises the respondent's behaviour as "harassment" or "deliberate" (rather than using neutral language like "the behaviour you described") may reach the respondent through social channels before formal mediation begins — escalating the dispute. South African community schemes often have WhatsApp groups where such content circulates rapidly. Mitigation: system prompt must explicitly forbid accusatory language; deEscalationTip must be framed around observer behaviour, mot attributed motive.

4. **Category misalignment with CSOS taxonomy creating audit trail inconsistency.** The AI suggests `suggestedCategory: "DAMAGE"` for a leaking common-property roof. A moderator later reclassifies it as COMMON_PROPERTY. The DisputeEvent log shows both — a CSOS export could appear internally inconsistent. While the AI output is advisory and not persisted in the dispute record, the frontend intake wizard (Phase 107) pre-populates the category dropdown with the AI's suggestion. If the user accepts it without review, the mismatch enters the formal record. Mitigation: the `suggestedCategory` is a suggestion; the intake wizard must allow the user to override before submission, and the formal DisputeCase record should never reference the AI classification.

### Regulatory / Compliance Context

**POPIA (Protection of Personal Information Act, No. 4 of 2013)** — South Africa's data protection law, fully effective as of 1 July 2021. Key sections for this system:

- **Section 19 (Security Safeguards):** The responsible party (Netcomplex/Soralia Village HOA) must secure the integrity and confidentiality of personal information by taking appropriate, reasonable technical and organisational measures to prevent unlawful access or processing. Sending unsanitised dispute text to an AI provider constitutes unlawful processing if PII is included.
- **Section 71 (Automated Decision Making):** Prohibits decisions with legal consequences based solely on automated processing. This system is advisory-only (not binding, not persisted, no legal consequence), so Section 71 does not directly restrict it — but the advisory nature must be unambiguous in the UI.
- **Section 72 (Cross-Border Transfers):** Personal information may not be transferred outside South Africa unless the recipient is subject to laws providing adequate protection, or the data subject consents. AI providers (Anthropic US, OpenAI US) process data outside SA. Sanitisation to remove all PII before the API call is the primary mitigation — the transferred text should contain no "personal information" as defined in Section 1, making Section 72 inapplicable.

**CSOS Act (Community Schemes Ombud Service Act, No. 9 of 2011):**

- **Section 38:** Any person may apply to CSOS for dispute resolution if internal mechanisms fail or are unavailable.
- **Section 39:** CSOS may refer disputes to conciliation before adjudication.
- **Regulation 4 (GN R607 of 2016):** Applications must include a statement that internal dispute resolution was attempted. The dispute intake system — including this AI screen — forms part of the HOA's demonstrable internal mechanism.
- **Form 2:** The CSOS export generated by Phase 108 must satisfy Form 2 documentation requirements. The AI intake screen itself does not feed into the export (its output is not persisted), but miscategorisation at intake could create downstream audit trail inconsistencies.

**HOA Governance Obligations (Sectional Titles Schemes Management Act, No. 8 of 2011):** Body corporates must make internal dispute resolution available. The platform's dispute module — including the intake wizard — is the mechanism by which Soralia Village discharges this obligation. Failure to provide an accessible intake process could be cited in a CSOS application as "internal resolution was not genuinely available."

**Multi-Tenant SaaS Considerations:** Netcomplex serves multiple community schemes, each with their own POPIA obligations and CSOS scheme registration numbers. The AI capability (`ai.disputes.frivolityScreen`) is tenant-gated — a tenant that has not configured their `csos.schemeRegistration` setting should not have the disputes module enabled (ADVISORY-017 Risk R8). The intake screen must not process disputes for tenants where this precondition is unmet.

## 2. Framework Decision

**Selected Framework:** No AI framework — direct provider SDK call via Phase 104 AI pool (`@anthropic-ai/sdk` v0.106, `openai` v6.45)

**Version:** As installed (Phase 104 pool abstraction at `src/shared/api/ai/`)

**Rationale:**
The AI infrastructure (provider pool, quota management, usage tracking) already exists from Phase 104. Adding any framework would introduce unnecessary abstraction. A single `provider.complete()` call with JSON mode is simpler, faster, and keeps zero net-new dependencies. The intake screen is a thin consumer — it sends structured input and receives structured output.

**Alternatives Considered:**

| Framework         | Ruled Out Because                                                        |
| ----------------- | ------------------------------------------------------------------------ |
| OpenAI Agents SDK | Overkill for a single completion call; adds vendor dependency            |
| LangChain         | Abstraction overhead unnecessary; project already has direct SDK clients |
| CrewAI            | Multi-agent orchestration doesn't apply to structured extraction         |

**Vendor Lock-In Accepted:** No — Phase 104 pool is model-agnostic (Anthropic, OpenAI, DeepSeek)

### Entry Point Pattern — Intake Screen Route

The canonical pattern (from Phase 104 SUPPLEMENTAL-2 §5, adapted for the intake screen). This is the **complete pool call lifecycle** — every AI-consuming route follows this pattern:

```typescript
// src/app/api/disputes/intake-screen/route.ts
import { z } from 'zod';
import {
  apiError,
  apiInternalError,
  apiSuccess,
  db,
  getSessionAndRole,
  logError,
  rateLimitByUser,
} from '@api/server';
import {
  getAiProvider,
  isAiCapabilityEnabled,
  checkQuota,
  recordUsage,
  AI_MODELS,
} from '@api/server';
import type { AiCapabilityKey } from '@entities/tenant/server';
import { withTenant } from '@entities/tenant/server';
import { sanitizeDescriptionForAi } from '@/shared/lib/dispute/sanitize'; // Phase 106 — new

// ── Zod schema: validated before AI call ────────────────────────────
const intakeScreenRequestSchema = z.object({
  description: z.string().min(10).max(5000),
  disputeId: z.string().uuid().optional(), // for usage tracking
});

// ── System prompt: module-level constant for prompt engineering hygiene ──
const INTAKE_SYSTEM_PROMPT = `You are a community dispute intake assistant for a residential community management platform. Assess the following dispute description and return valid JSON. Follow these rules:

1. toneScore: 0 (calm/factual) to 10 (highly emotional/personal attacks)
2. issueClarity: 0 (vague) to 10 (specific, identifiable issue with dates/behaviors)
3. likelyFrivolous: true only if no actionable grievance is identifiable (no specific rule, damage, or obligation mentioned)
4. suggestedCategory: one of "NOISE","PETS","PARKING","BOUNDARIES","COMMON_PROPERTY","LEVY_DISPUTE","RULE_ENFORCEMENT","GOVERNANCE","CONDUCT","DAMAGE","OTHER"
5. deEscalationTip: a constructive, single-sentence tip IF toneScore >= 7; otherwise null. Never use inflammatory or accusatory language. Frame tips around focusing on specific dates, behaviors, and applicable rules.

Return ONLY the JSON object, no markdown, no explanation.`;

export const maxDuration = 15; // seconds — Next.js serverless timeout guard

export async function POST(request: Request) {
  try {
    // ── 0. Auth & rate limiting ──────────────────────────────────
    const auth = await getSessionAndRole(request);
    if (!auth) return apiError('AUTH_REQUIRED', 'Authentication required', 401);

    const rateLimitResult = await rateLimitByUser(auth.userId, {
      windowMs: 60_000,
      maxRequests: 5, // tighter limit than translate — frivolity checks are discretionary
    });
    if (rateLimitResult) return rateLimitResult;

    // ── 1. Input validation (Zod) ─────────────────────────────────
    const parsed = intakeScreenRequestSchema.safeParse(await request.json());
    if (!parsed.success) {
      return apiError('VALIDATION_ERROR', 'Invalid request body', 400, parsed.error.flatten());
    }

    const { description, disputeId } = parsed.data;

    // ── 2. Tenant context ─────────────────────────────────────────
    const { tenantId } = await withTenant();
    const capability: AiCapabilityKey = 'ai.disputes.frivolityScreen';

    // ── 3. Capability check (tenant opt-in gating) ────────────────
    if (!(await isAiCapabilityEnabled(tenantId, capability))) {
      return apiError(
        'FEATURE_DISABLED',
        'AI intake screening is not enabled for this community.',
        503
      );
    }

    // ── 4. Quota check (pre-flight — does not consume tokens) ─────
    const quota = await checkQuota(tenantId, capability, db);
    if (!quota.allowed) {
      return apiError(
        'FEATURE_DISABLED',
        `AI token quota exhausted (${quota.remainingTokens} remaining). Upgrade or wait until next billing period.`,
        429,
        { code: 'AI_QUOTA_EXHAUSTED', remainingTokens: quota.remainingTokens }
      );
    }

    // ── 5. Get provider ──────────────────────────────────────────
    const provider = await getAiProvider(tenantId);
    if (!provider.isAvailable()) {
      return apiError('FEATURE_DISABLED', 'AI service temporarily unavailable', 503);
    }

    // ── 6. Sanitise description (POPIA — strip PII before leaving server) ──
    const sanitised = sanitizeDescriptionForAi(description);

    // ── 7. Call AI ───────────────────────────────────────────────
    const start = Date.now();
    let result: { text: string; provider: string; tokensUsed: number };
    let success = true;
    let errorCode: string | undefined;

    try {
      const completion = await provider.complete(sanitised, {
        capability,
        systemPrompt: INTAKE_SYSTEM_PROMPT,
        maxTokens: 500,
        temperature: 0,
        jsonMode: true,
      });
      result = {
        text: completion.text,
        provider: completion.provider,
        tokensUsed: completion.tokensUsed ?? 0,
      };
    } catch (err) {
      success = false;
      errorCode = err instanceof Error ? err.message.slice(0, 50) : 'UNKNOWN';
      result = { text: '', provider: provider.name, tokensUsed: 0 };
    }

    // ── 8. Record usage (ALWAYS — even on failure, prevents retry-spam) ──
    const modelId =
      provider.name === 'anthropic'
        ? AI_MODELS.ANTHROPIC
        : provider.name === 'openai'
          ? AI_MODELS.OPENAI
          : AI_MODELS.DEEPSEEK;

    await recordUsage(
      {
        tenantId,
        capability,
        userId: auth.userId,
        referenceId: disputeId,
        provider: result.provider,
        model: modelId,
        inputTokens: estimateInputTokens(sanitised),
        outputTokens: result.tokensUsed ?? 0,
        durationMs: Date.now() - start,
        success,
        errorCode,
      },
      db
    );

    // ── 9. Handle result ─────────────────────────────────────────
    if (!success) {
      logError(
        { component: 'disputes-intake', operation: 'POST', provider: provider.name },
        'AI frivolity screening call failed',
        errorCode
      );
      // Graceful degradation: intake wizard skips this step
      return apiError(
        'FEATURE_DISABLED',
        'AI screening temporarily unavailable — you may proceed without it.',
        503
      );
    }

    // ── 10. Parse and validate AI output ──────────────────────────
    if (!result.text) {
      // Empty response → return safe defaults (never block the user)
      return apiSuccess({
        toneScore: 0,
        issueClarity: 5,
        likelyFrivolous: false,
        suggestedCategory: 'OTHER',
        deEscalationTip: null,
      });
    }

    try {
      const parsed = JSON.parse(result.text);
      // Validate shape before returning (defense-in-depth)
      return apiSuccess({
        toneScore: clamp(parsed.toneScore, 0, 10),
        issueClarity: clamp(parsed.issueClarity, 0, 10),
        likelyFrivolous: Boolean(parsed.likelyFrivolous),
        suggestedCategory: parsed.suggestedCategory ?? 'OTHER',
        deEscalationTip: parsed.deEscalationTip ?? null,
      });
    } catch {
      // Malformed JSON — safe defaults
      return apiSuccess({
        toneScore: 0,
        issueClarity: 5,
        likelyFrivolous: false,
        suggestedCategory: 'OTHER',
        deEscalationTip: null,
      });
    }
  } catch (error) {
    logError({ component: 'disputes-intake', operation: 'POST' }, 'Intake request failed', error);
    return apiInternalError();
  }
}

// ── Helpers (co-located in route file or extracted to shared lib) ──

/** Rough token estimator — chars ÷ 4 + 20% buffer (matches translate/route.ts pattern) */
function estimateInputTokens(text: string): number {
  return Math.ceil(text.length * 0.27 * 1.2);
}

function clamp(value: unknown, min: number, max: number): number {
  const n = Number(value);
  if (isNaN(n)) return min;
  return Math.max(min, Math.min(max, n));
}
```

### Common Pitfalls

1. **Calling `provider.complete()` before `checkQuota()`** — The pool tracks quota per capability. Calling `checkQuota()` first prevents wasted calls on exhausted tenants. Under `HARD_STOP` policy, the call will be denied. The translate route (line 62) and SUPPLEMENTAL-2 exemplify: capability check → quota check → provider → call.

2. **Skipping `recordUsage()` on failure** — The pool's `recordUsage()` must be called even when the AI call throws. If skipped, a malicious user can retry-spam without consuming quota. `pool.ts` JSDoc enforces: "failures still count against quota to prevent retry-spam abuse."

3. **Anthropic + `jsonMode: true` has no SDK effect** — Unlike OpenAI's `response_format: { type: 'json_object' }`, the Anthropic SDK has no native JSON mode. The current `AnthropicProvider` (line 19–36 of `anthropic.ts`) does not inspect the `jsonMode` option. **Mitigation**: the system prompt must explicitly demand JSON-only output. For production reliability, consider routing structured output calls to OpenAI when `jsonMode: true` is critical, or add a `{ "` prefill (Anthropic prefill pattern) to the `AnthropicProvider` at the pool level.

4. **Not sanitising description before sending to AI** — Dispute descriptions routinely contain surnames, unit numbers, and direct identifiers. ADVISORY-017 §7 and CONTEXT.md mandate a sanitisation pass before the AI call. This must happen **server-side** (not just client-side) — the `sanitizeDescriptionForAi()` utility is the single choke point.

5. **Returning AI output to the client without shape validation** — The AI may return missing fields or unexpected types. The route MUST defensively validate every field: clamp numerics, coerce booleans, default missing strings. Malformed JSON → safe defaults (never throw to the client). This pattern is demonstrated in Step 10 of the entry point above (lines parsing `result.text`).

**Core Pattern:**

The intake screen uses the **pool call lifecycle pattern** (documented in full in Section 3 Entry Point). The 10-step sequence is:

```
0. Auth + rate limit
1. Zod validation (intakeScreenRequestSchema)
2. Tenant context (withTenant)
3. Capability check (isAiCapabilityEnabled → 'ai.disputes.frivolityScreen')
4. Quota check (checkQuota → 429 if exhausted)
5. Get provider (getAiProvider → 503 if NullProvider)
6. Sanitise description (sanitizeDescriptionForAi — POPIA compliance)
7. Call AI (provider.complete with jsonMode + systemPrompt)
8. Record usage (recordUsage — ALWAYS, even on failure)
9. Handle errors (503 graceful degradation, no blocking)
10. Parse + validate + return (JSON.parse → field coercion → apiSuccess)
```

**Critical design principle: the AI output is advisory-only.** The route never returns an error to the user because the AI failed — it returns safe defaults instead. The intake wizard (Phase 107) skips the frivolity step entirely when AI is unavailable, collapsing from 4 stages to 3 with zero user-visible indication that anything is missing.

**Tool Use:**

No tool calling, no function calling. This is a **single-turn structured classification call** — the prompt describes the output format and the model responds with JSON. The intake screen does not need:

- Vector DB / embeddings (no RAG)
- Tool definitions (no multi-step reasoning)
- Streaming (response is ~150 chars — stream overhead exceeds benefit)
- Conversation history (stateless — each call is independent)

**State Management:**

The AI intake screen is **fully stateless** — the response is never persisted to the database. Key implications:

- **No DisputeCase field mutation**: The AI response is never written to `disputeCases`, `disputeEvents`, or any table. It exists only in the HTTP response body.
- **No caching needed**: Each call is independent; users can re-screen the same description without cache invalidation concerns.
- **Usage tracking is the only side effect**: `recordUsage()` writes to `tenantAiUsages` and `aiUsageEvents` (pool ledger), but these are operational/infrastructure records, not dispute domain state.
- **Frontend state management** (Phase 107): The intake wizard's `useDisputeIntake.ts` state machine manages which steps are visible. When AI is unavailable, the `frivolity` step is conditionally excluded from the steps array.

**Context Window Strategy:**

The intake screen has the **simplest possible context management** — a single short user message:

- **User content**: sanitised dispute description, max 5,000 chars (~1,250 tokens)
- **System prompt**: ~350 tokens (INTAKE_SYSTEM_PROMPT)
- **Total context**: ~1,600 tokens — well under every provider's floor (Haiku: 200K, GPT-4o-mini: 128K, DeepSeek: 128K)

No truncation, summarisation, or chunking strategy is required. The `z.string().max(5000)` Zod validation on the request body is the sole context window guard — it rejects oversized input before the AI call.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns adapted for **TypeScript/Zod + direct provider SDK** (no framework). The project uses Zod v3.25 for schema validation — all "Pydantic" references below are translated to their TypeScript/Zod equivalents.

### 4b.1 Structured Outputs with Zod

The AI intake screen must return a predictable shape. The approach uses a **Zod schema as the source of truth** for the output contract, with defensive field-level coercion after `JSON.parse()`. Since the pool uses raw SDK calls (not a framework with built-in structured output), validation is post-hoc.

#### Output Schema (Zod)

Define this in `src/shared/lib/dispute/intake-screen-output.ts` (new file, Phase 106):

```typescript
import { z } from 'zod';

/** Canonical AI output shape for the intake screen frivolity check. */
export const intakeScreenOutputSchema = z.object({
  toneScore: z.number().int().min(0).max(10).default(0),
  issueClarity: z.number().int().min(0).max(10).default(5),
  likelyFrivolous: z.boolean().default(false),
  suggestedCategory: z.string().default('OTHER'),
  deEscalationTip: z.string().nullable().default(null),
});

export type IntakeScreenOutput = z.infer<typeof intakeScreenOutputSchema>;

/**
 * Parse raw AI response text into the canonical output shape.
 * Never throws — returns safe defaults on any failure.
 */
export function parseIntakeScreenOutput(raw: string): IntakeScreenOutput {
  try {
    const parsed = JSON.parse(raw);
    return intakeScreenOutputSchema.parse(parsed);
  } catch {
    // Safe defaults — advisory screen never blocks the user
    return {
      toneScore: 0,
      issueClarity: 5,
      likelyFrivolous: false,
      suggestedCategory: 'OTHER',
      deEscalationTip: null,
    };
  }
}
```

#### Integration with the Pool Pattern

The route (Step 10 in Section 3) calls `parseIntakeScreenOutput(result.text)` after receiving the AI response:

```typescript
// Inside the route handler — Step 10 of the pool lifecycle
try {
  const output = parseIntakeScreenOutput(result.text);
  return apiSuccess(output);
} catch {
  // parseIntakeScreenOutput already handles this internally with safe defaults,
  // but the outer catch is belt-and-suspenders for unexpected JSON.parse explosions
  return apiSuccess({
    toneScore: 0,
    issueClarity: 5,
    likelyFrivolous: false,
    suggestedCategory: 'OTHER',
    deEscalationTip: null,
  });
}
```

#### Retry Logic

The intake screen does NOT retry. Reasoning:

- **Advisory output**: A failed call → safe defaults, not a critical UX failure.
- **Quota impact**: Retrying burns tokens on a potentially-broken provider. The pool's `recordUsage` counts failures against quota to prevent retry-spam.
- **User experience**: A loading spinner for 3 retries (~15 seconds total at worst) is worse UX than instantly returning safe defaults and letting the user proceed.
- **Alternative**: If the intake wizard wants a re-screen, the user can click "Check again" — this is a fresh request, not an automatic retry.

If a retry were needed in the future (e.g., for a critical, non-advisory AI call), implement at the pool level with exponential backoff, max 2 retries, and only on 5xx / network errors (not 4xx or JSON parse errors).

### 4b.2 Async-First Design

**How Async Works in This Pattern:**

Next.js App Router route handlers are `async` functions. The pool call lifecycle is fully async:

```typescript
export async function POST(request: Request) {
  // All pool operations are async — await each sequentially
  const auth = await getSessionAndRole(request);       // Better Auth session lookup
  const { tenantId } = await withTenant();              // Tenant context from host header
  const capable = await isAiCapabilityEnabled(tenantId, capability); // DB read
  const quota = await checkQuota(tenantId, capability, db);         // DB read
  const provider = await getAiProvider(tenantId);                   // Pool factory
  const result = await provider.complete(sanitised, options);       // HTTP call to AI API
  await recordUsage({ ... }, db);                                   // DB write
  // ...
}
```

**The One Common Mistake — Blocking the Event Loop:**

In Next.js serverless environments, the entire route handler runs in a single request context. **Never perform synchronous CPU-intensive work between async calls** — it blocks the event loop for all concurrent requests on the same instance. The `estimateInputTokens()` helper is a `Math.ceil` operation (sub-microsecond) so it's safe, but:

- ❌ **Bad**: `const sanitised = someHeavySyncRegex(description)` before the AI call
- ✅ **Good**: Use `sanitizeDescriptionForAi()` which is a single regex pass on <5KB of text

**Stream vs. Await:**

- **Stream**: Not used. The intake screen returns ~150 chars of JSON. Streaming adds HTTP framing overhead (Server-Sent Events, chunked transfer encoding) without UX benefit. Reserve streaming for chat interfaces where token-by-token rendering creates perception of speed.
- **Await**: Used exclusively. The entire response is buffered, validated against the Zod schema, and returned in a single `apiSuccess()` call. This ensures structured output validation happens before any bytes reach the client.

### 4b.3 Prompt Engineering Discipline

**System vs. User Prompt Separation:**

The pool's `AiCompletionOptions.systemPrompt` maps directly to the provider's system message:

- **Anthropic**: `system` parameter in `messages.create()` — semantically a top-level system instruction, not a message in the conversation.
- **OpenAI**: `role: 'system'` message — the first message in the array, treated as instruction.

```typescript
// System prompt: instructions, rules, output format (IMMUTABLE — same for all calls)
const INTAKE_SYSTEM_PROMPT = `...`; // defined at module level

// User prompt: the sanitised description (VARIABLE — one per call)
const result = await provider.complete(sanitisedDescription, {
  systemPrompt: INTAKE_SYSTEM_PROMPT,
  // ...
});
```

**Key rules enforced:**

1. The system prompt is a **module-level constant** — never constructed dynamically, never interpolated with user input. This prevents prompt injection and makes the prompt auditable in git.
2. The user prompt is **the sanitised description only** — no extra instructions, no "here is my dispute:", no conversational wrapper. Minimal user content reduces token waste and prevents the model from getting confused by meta-commentary.
3. The system prompt **explicitly names the output format** — including enum values for `suggestedCategory` — so the model knows the exact set of valid values without needing function calling.

**Few-Shot Guidance:**

This system type uses **zero-shot** (no examples). The system prompt describes the rules, not examples. Rationale:

- **Narrow domain**: Dispute categories (NOISE, PETS, etc.) are self-explanatory. The model doesn't need examples to classify "barking dog at night" → PETS.
- **Token budget**: Few-shot examples add ~100 tokens each. For a 300-token call, 2 examples nearly double the cost.
- **Calibration risk**: Examples can anchor the model to a specific severity range, causing miscalibrated `toneScore` for outlier disputes.

If performance is poor in production, add **dynamic few-shot retrieval** (Phase 108): store 5 labeled examples in a config table, retrieve by suggestedCategory, inject inline. But start with zero-shot first.

**Set maxTokens Explicitly:**

```typescript
maxTokens: 500, // in AiCompletionOptions — NEVER leave unbounded
```

- **Bounded output**: The intake output is ~150 tokens. 500 provides 3.3× safety margin.
- **Cost controls**: `maxTokens` caps the worst-case cost per call. Without it, a model hallucinating a long response wastes tokens and money.
- **Defaults don't protect you**: Both `AnthropicProvider` and `OpenAiProvider` default to `maxTokens: 1000` — override for each capability based on expected output size.

### 4b.4 Context Window Management

**System type: Structured Data Extraction / Advisory Response**

This is the simplest context management scenario — single short message, well under limits.

- **Total context**: ~1,600 tokens (350 system + 1,250 user max) vs. 128K+ provider windows. **No management required.**
- **Zod guard**: The `z.string().max(5000)` validation is the sole context limiter. Clients cannot submit descriptions larger than ~1,250 tokens.
- **No RAG**: No retrieval step. The user's description IS the input — there's no knowledge base to search.
- **No conversation**: Each call is stateless. No conversation history to summarize or compact.
- **Future scalability** (Phase 108+): If the intake screen ever adds evidence summarisation (reading uploaded PDFs), the context strategy would need to handle multi-turn summarisation. For now, this is out of scope.

## 6. Guardrails

> Decision rule: "If this goes wrong, would it be catastrophic?" → Yes = online guardrail. No = offline flywheel.
> Guardrails add latency — keep online guardrails minimal. The intake screen already has 6 pre-AI steps (auth, validation, tenant, capability, quota, provider) that act as structural guardrails — only the AI-output-specific guardrails are documented below.

### 6.1 Online Guardrails (Real-Time — Runs on Every Request)

| #      | Guardrail                              | Failure Mode Addressed                                                   | Trigger                                                                                                                                                                                                                                                                   | Intervention                                                                                                                                                                                     | Latency Budget                        |
| ------ | -------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------- |
| **G1** | **PII Sanitisation Execution**         | FM1: PII leakage to AI provider (POPIA cross-border violation)           | `sanitizeDescriptionForAi()` is the single choke point — called immediately before `provider.complete()`. The guardrail is structural: the route code MUST call `sanitizeDescriptionForAi(description)` before any AI call. No dynamic trigger — enforced at code review. | **Block AI call** — if `sanitizeDescriptionForAi()` throws (unexpected), route returns 503 graceful degradation (never sends raw description).                                                   | <5ms (single regex pass)              |
| **G2** | **System Prompt Immutability**         | FM2: Prompt injection via user input leaking into system instructions    | `INTAKE_SYSTEM_PROMPT` is a module-level `const` — never interpolated with user input, never constructed dynamically. User content is passed as the user message only (no system-prompt injection vector).                                                                | **Prevent** — structural enforcement via code pattern. TypeScript `const` assertion. PR review gate: any `provider.complete()` call that interpolates user input into `systemPrompt` is a block. | 0ms (compile-time)                    |
| **G3** | **Malformed JSON Safe Defaults**       | FM3: Invalid JSON response crashes intake screen                         | `parseIntakeScreenOutput()` wraps `JSON.parse()` + `intakeScreenOutputSchema.parse()` in try/catch. Any failure → safe defaults returned.                                                                                                                                 | **Fall through to safe defaults** — user never sees an error, intake wizard proceeds without AI step. Log the parse failure server-side for flywheel review.                                     | <5ms (JSON.parse + Zod)               |
| **G4** | **Field Coercion Belt-and-Suspenders** | FM3: AI returns correct JSON but wrong types (e.g., `toneScore: "high"`) | After `JSON.parse()`, every field is defensively coerced: `clamp(toneScore, 0, 10)`, `Boolean(likelyFrivolous)`, `suggestedCategory ?? 'OTHER'`, `deEscalationTip ?? null`. Zod `.default()` provides second layer.                                                       | **Coerce and continue** — wrong types are silently normalized. No error returned to user.                                                                                                        | <2ms (Number/Boolean/String coercion) |
| **G5** | **Quota Pre-Flight Check**             | FM4: Quota exhaustion consumes pool capacity needed for other modules    | `checkQuota()` runs before every AI call. Returns HTTP 429 with `code: 'AI_QUOTA_EXHAUSTED'` if `HARD_STOP` tier is exhausted. `recordUsage()` always called (even on failure) to prevent retry-spam bypass.                                                              | **Block AI call** — return 429 before token consumption. Admin notification triggered at 80% threshold by `recordUsage()`.                                                                       | <20ms (DB read)                       |

### 6.2 Offline Flywheels (Batch Analysis — Feeds Continuous Improvement)

| #      | Metric                             | Failure Signal                                                                                          | Sampling Strategy                                                                                                                                                                                                                                                                                                                  | Action on Degradation                                                                                                                                                                                                                                                                                                       |
| ------ | ---------------------------------- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **F1** | **Frivolity Classification Drift** | `likelyFrivolous: true` rate shifts >20% from baseline (expect 15-25% for community disputes)           | **Smart sampling**: weight toward (a) interactions where user proceeded with filing despite `likelyFrivolous: true` (potential false positive), (b) interactions where `toneScore > 7` (emotional signals may confuse classifier), (c) every 50th intake screen call (uniform baseline). Sample size: 10-15/month.                 | Review sampled interactions with HOA Board Member. | **F2** | **De-escalation Tone Drift**       | LLM judge tone score flags >20% of de-escalation tips as "dismissive" or "inflammatory"                 | **Smart sampling**: weight toward (a) `toneScore >= 7` outputs (high-stakes — emotional filer receiving advice), (b) non-English descriptions (multi-language tone sensitivity), (c) random 10% uniform sample. Sample size: 20/month.                                                                                             | Run LLM judge (GPT-4o-mini with tone rubric) on sampled tips. If >20% flagged: (1) strengthen system prompt de-escalation rules, (2) add explicit counter-examples of bad de-escalation language to system prompt, (3) escalate to HOA Board Member for cultural sensitivity review if multi-language tone issues detected. |
| **F3** | **Category Accuracy Degradation**  | `suggestedCategory` mismatch rate vs. moderator-assigned category exceeds 30%                           | **Production sampling**: compare AI `suggestedCategory` against the `categoryId` field on the `DisputeCase` record where the moderator overrode the suggested category. Filter disputes where the moderator actively changed the category (rejected suggestion). Sample size: all moderator-overridden disputes (est. 5-10/month). | If mismatch rate exceeds 30%: (1) review CSOS taxonomy alignment in system prompt, (2) add worst-offending category pairs as explicit counter-examples, (3) Phase 108: consider removing AI category suggestion from pre-populated dropdown (make it fully manual selection with AI hint only).                             |
| **F4** | **PII Sanitisation Regression**    | Any PII pattern survives in production sanitised output (detected via regex audit of sampled responses) | **Batch audit**: run PII regex suite (South African patterns: surnames, unit numbers, vehicle plates, ID numbers, phone numbers) against a 5% uniform sample of logged sanitised descriptions. Sample size: all calls (total volume is ~5-20/month for 180-home community — audit everything).                                     | **Immediate Severity 1 incident**: if any PII survives in production, (1) halt AI intake screen via tenant capability toggle, (2) audit sanitisation utility for missing pattern, (3) report to POPIA Information Officer, (4) fix and re-enable after regression test passes.                                              |
| **F5** | **Latency & Cost Drift**           | p95 latency >2,000ms OR per-call token count >500                                                       | **Uniform sampling**: all calls logged via Pino with `durationMs` and `tokensUsed` fields from `recordUsage()`.                                                                                                                                                                                                                    | If p95 > 2,000ms: investigate provider latency, review model routing (is a heavier model being used?). ### 6.3 Guardrail Implementation Location

All online guardrails (G1–G5) are implemented **in-route** — co-located in `src/app/api/disputes/intake-screen/route.ts`. This keeps the guardrail logic visible, auditable, and free of framework overhead. No separate guardrail service or middleware layer — the 10-step pool call lifecycle (Section 3) already embeds every guardrail step.

Offline flywheels (F1–F5) run as **scheduled background jobs** (Vercel Cron Jobs or GitHub Actions scheduled workflow), not as request-time overhead.

## 7. Production Monitoring

> The intake screen is advisory-only with low volume (5–20 calls/month for 180-home community). Monitoring is lightweight — focused on operational health signals rather than building a heavy observability stack for a thin AI consumer.

### 7.1 Tracing & Observability

**Tracing Tool:** **Pino** (structured JSON logging — already in project via `logError()`). No external tracing platform is warranted for this volume.

**Rationale for NOT using Arize Phoenix / Langfuse / LangSmith:**

- This is a TypeScript/Next.js project — Arize Phoenix is Python-centric and would require a separate Python service.
- Langfuse/LangSmith are designed for high-volume production LLM pipelines (100+ calls/day). The intake screen does 5–20 calls/month.
- The pool's `recordUsage()` ledger (`tenantAiUsages` table) already captures per-call telemetry: `provider`, `model`, `inputTokens`, `outputTokens`, `durationMs`, `success`, `errorCode`.
- Pino structured logging with Supabase log drain provides sufficient observability without additional infrastructure.

**Logging Pattern (every AI call):**

```typescript
// Success log — emitted after recordUsage()
logger.info(
  {
    component: 'disputes-intake',
    operation: 'POST',
    tenantId,
    provider: result.provider,
    model: modelId,
    inputTokens: estimateInputTokens(sanitised),
    outputTokens: result.tokensUsed,
    durationMs: Date.now() - start,
    toneScore: output.toneScore,
    likelyFrivolous: output.likelyFrivolous,
    suggestedCategory: output.suggestedCategory,
  },
  'intake-screen-ai-call'
);

// Failure log — emitted in catch block
logError(
  { component: 'disputes-intake', operation: 'POST', provider: provider.name },
  'AI frivolity screening call failed',
  errorCode
);
```

**If future volume justifies tracing** (500+ calls/month, multi-tenant scale): adopt OpenTelemetry via `@vercel/otel` (native Next.js integration) with an OTLP exporter to a self-hosted collector. For now, this is unnecessary.

### 7.4 Smart Sampling Strategy for Human Review

Production volume is low (5–20 calls/month for 180-home community). **Sample all calls** during the first 3 months — the total is trivially reviewable. After baseline is established:

| Sampling Rule                                                                  | Weight | Rationale                                                                                                 |
| ------------------------------------------------------------------------------ | ------ | --------------------------------------------------------------------------------------------------------- |
| **All calls with `toneScore >= 8`**                                            | 100%   | High-emotion disputes — de-escalation quality matters most here. Review for inflammatory language.        |
| **All calls where user proceeded with filing despite `likelyFrivolous: true`** | 100%   | Potential false positives — user disagreed with AI assessment. Review for frivolity classification error. |
| **All calls where `suggestedCategory` was overridden by moderator**            | 100%   | Potential category misclassification — review for CSOS taxonomy alignment.                                |
| **All calls where AI failed (safe defaults returned)**                         | 100%   | Degradation events — review for root cause (provider outage vs. malformed JSON vs. quota).                |
| **Random 20% of all other calls**                                              | 20%    | Uniform baseline — catch unexpected failure modes not covered by signal-based sampling.                   |

**Review cadence:** Monthly (aligned with the HOA board meeting cycle). Review findings feed the offline flywheels (F1–F5) and reference dataset expansion.

### 7.5 Dashboard (Supabase + Pino)

No dedicated AI observability dashboard is warranted at this volume. Existing infrastructure suffices:

- **Supabase SQL queries**: `tenantAiUsages` table for quota utilisation, success rate, per-provider latency
- **Pino log search**: Vercel Log Drain or Supabase `logs` table for per-call structured log inspection
- **Manual monthly query**: `SELECT date_trunc('month', created_at), COUNT(*), AVG(duration_ms), SUM(tokens_used) FROM ai_usage_events WHERE capability = 'ai.disputes.frivolityScreen' GROUP BY 1;`

If volume exceeds 500 calls/month (multi-tenant scale), consider adding a lightweight Retool or Metabase dashboard pointing at the Supabase read replica. For now, these SQL queries run in <100ms.
