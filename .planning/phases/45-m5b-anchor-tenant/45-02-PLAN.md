Per RESEARCH.md Pattern 3 (event-driven auto-escalation) and the code example at RESEARCH.md lines 342-389 — create two API route files.

**Step A — Create src/app/api/merits/route.ts (GET list + POST create):**

GET handler:

- `withTenant()` for tenant isolation
- Auth: `auth.api.getSession()` → check `hasPermission(role, 'users')`
- Query params: `userId` (optional filter), `page` (default 1), `limit` (default 20)
- Query `behaviorRecords` with `notDeleted()`, optional userId filter, order by createdAt DESC
- Count total for pagination, return `apiSuccess({ entries, pagination: { page, limit, total, hasMore } })`

POST handler (create behavior entry):

- `withTenant()` + `requireAssistScope(request, 'full')` + auth check `hasPermission(role, 'users')`
- Parse body: `{ userId, behaviorType, reason, description? }`
- Validate behaviorType ∈ ['MERIT', 'WARNING', 'INFRACTION']
- Validate reason: string, min 3 chars
- Use `db.transaction(async tx => { ... })` — exactly like suspend route:
  1. `const currentStanding = await calculateStanding(body.userId, tenantId, tx)`
  2. `const pointDelta = BEHAVIOR_POINTS[body.behaviorType]`
  3. `const newStanding = currentStanding + pointDelta`
  4. Insert behaviorRecord with `id: crypto.randomUUID()`, standingBefore, standingAfter, createdById, createdAt
  5. `await checkAndEscalateStanding(body.userId, newStanding, tenantId, tx)`
  6. Return the created record
- Write audit log: `writeAuditLog({ action: 'BEHAVIOR_RECORD_CREATED', actorId, targetId, tenantId, details: { behaviorType, reason, points: pointDelta, standingBefore, standingAfter } })`
- Return `apiCreated(result)`

**Step B — Create src/app/api/merits/[id]/route.ts (GET/PATCH/DELETE by id):**

GET handler:

- `withTenant()` + auth check `hasPermission(role, 'users')`
- Query single behaviorRecord by id + tenantId + notDeleted()
- 404 if not found, return `apiSuccess(entry)`

PATCH handler (update reason/description — points are immutable):

- Same auth + scope guards as POST
- Validate body: only `reason` and `description` are mutable
- Update record (only reason and description fields)
- Return `apiSuccess(updated)`

DELETE handler (soft-delete):

- Same auth + scope guards
- Soft-delete: `tx.update(behaviorRecords).set({ deletedAt: new Date() }).where(...)`
- Recalculate standing for the user (standing changes since the deleted entry's points are removed)
- Write audit log: `writeAuditLog({ action: 'BEHAVIOR_RECORD_DELETED', ... })`
- Return `apiSuccess({ deleted: true })`

| ----------------- | --------------------------------- | -------------------- |
| Behavior records  | Medium (resident standing data)   | BehaviorRecord table |

## STRIDE Threat Register

| Threat ID | Category               | Component               | Disposition | Mitigation Plan                                                                                         |
| --------- | ---------------------- | ----------------------- | ----------- | ------------------------------------------------------------------------------------------------------- |
| T-45-07   | Spoofing               | POST /api/merits        | mitigate    | `auth.api.getSession()` verifies admin identity; `requireAssistScope('full')` prevents staff escalation |
| T-45-08   | Tampering              | Standing calculation    | mitigate    | Drizzle transaction wraps insert + standingBefore/After + escalation — atomic, no partial state         |
| T-45-09   | Tampering              | Points field            | mitigate    | Points are calculated server-side from BEHAVIOR_POINTS constant — client cannot override                |
| T-45-10   | Repudiation            | Behavior entry creation | mitigate    | `writeAuditLog` on every CREATE and DELETE with actorId, targetId, standing values                      |

| T-45-13   | Denial of Service      | standings recalculation | accept      | SUM query is O(n) per user; 180-home community size makes this negligible                               |
