# Phase 44 — UI Design Contract

> Visual and interaction contract for Phase 44 (M5a Hardening & Launch Readiness).
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **UI Scope: No New UI.** Phase 44 is an architectural hardening phase, not a feature
> phase. The executed plans (44-01 SHIPPED, 44-02–44-08+ TBD) are observability
> infrastructure, code refactors, dead-code removal, FSD debt remediation, and
> advisory resolution. The phase touches a small set of **existing** UI surfaces
> (Header, Footer, SideDrawer, MobileMenu, SpaceChrome, MobileSpaceBar, GateGuard,
> ~10 admin widgets, MyHomeSpace) but introduces **no new visual designs, no new
> components, no new copy, and no new user journeys.**
>
> This UI-SPEC is therefore a **carry-forward contract** — it documents the
> existing design system that any touched UI must respect, names the surfaces
> each plan will edit, and gives the executor a regression-prevention checklist.
> Sections that would otherwise declare new visual choices (CTA copy, color
> splits, typography scale) are explicitly marked **"no new content"** rather than
> fabricated.

the request to the user **before** writing the code.

**No new content.** Phase 44 introduces no new color tokens.

| Role            | Value                                                   | Usage                                                   |
| --------------- | ------------------------------------------------------- | ------------------------------------------------------- |
| Dominant (60%)  | `#F3F4F6` (soralia-light, `bg-soralia-light` on body)   | Page background, content surfaces                       |

- Primary buttons (`bg-soralia-primary` / `text-soralia-primary`)
- Active navigation items (Header, MobileMenu, SpaceChrome active state)
- Focus rings (shadcn ring color tokens resolve to primary)
- Link color in body copy

Lapis & Gold-Vein sub-palette (per `globals.css`):

- `--lapis-deep` `#0F1F4A` — premium/header accents
- `--lapis-mid` `#1E3A7A` — secondary brand
- `--lapis-azure` `#4A7AB5` — links, info
- `--gold-vein` `#C8A84B` — premium-tier accents, conservation/campaign surfaces
- `--vellum` `#F2ECD8` / `--vellum-light` `#EAF0FA` — campaign surfaces

> **Multi-tenant theming:** Colors are CSS-variable-driven and overridable per
> tenant via `src/app/layout.tsx` (per AGENTS.md: "Dynamic tenant theming wired
> via layout.tsx"). All Phase 44 work must preserve the
> `var(--primary-color, #4F46E5)` fallback pattern — never hard-code `#4F46E5`
> in component code.

Plan 44-02 introduces an observability stack. These are **external tools, not
project UI** — they don't follow this design contract. They are documented here
only so the executor and the M5b launch team know what dashboards to monitor.

| Tool                     | Surfaces visible to whom          | Status                 |
| ------------------------ | --------------------------------- | ---------------------- |
| Vercel Web Vitals (free) | All plans; p75 LCP/TTFB           | Built-in; no setup     |
| Vercel Monitoring (Pro)  | p75 server timings, 5xx           | Active                 |
| Vercel Logs (free/Pro)   | Pino structured logs              | Active                 |
| Sentry (org TBD)         | Errors, sessions, traces, replays | New (44-02)            |
| `@vercel/otel` (new)     | OTel framework spans              | New (44-02)            |
| Pino (already installed) | Structured app logging            | Extended, not replaced |

**Critical config (44-02):** `Sentry.init({ skipOpenTelemetrySetup: true })` —
without this flag, Sentry and `@vercel/otel` fight over the global OTel provider
and one goes silent. Per Phase 44 RESEARCH.md §3.3.

**PII scrubbing (44-02):** `sendDefaultPii: false` + `beforeSend` scrubber for
`user.email`, `body.content` (chat). Sentry's default scrubbing does not catch
chat content. Documented in RESEARCH.md §3.6.

**No Sentry UI in the project.** Sentry's own dashboard (sentry.io) is the
review surface; it is not built into the project. The launch team uses Sentry's
web UI to triage issues — no design contract applies.

## Open Questions for Plans to Answer as They Execute

These are UI-adjacent questions that surface as the plans execute. The
**researcher could not pre-answer them** because the answers depend on the
exact code the plans produce. The executor and checker should resolve them
per-plan.

1. **44-06 cs5 MyHomeSpace split:** Does the orchestrator need to manage any
   client-side state that crosses the three sub-components, or is each
   sub-component self-contained with props? (Affects whether a `useReducer`
   or just prop drilling is needed — both are acceptable per AGENTS.md.)

2. **44-05 `brp` / `huo` field renames in MyHomeSpace:** The `residencyType`
   and `occupantType` fields may appear in MyHomeSpace's resident-edit form.
   The exact label change must flow through i18n. Per Phase 41 precedent:
   add the new key to all 4 locales before renaming the field.

3. **44-04 usePageFlags → useGateContext timing:** If a touched component
   currently relies on `usePageFlags` returning synchronous defaults during
   SSR, the migration to `useGateContext` (which returns null while loading)
   may introduce a hydration flash. The plan must verify with
   `ErrorBoundary` + Suspense patterns before shipping.

4. **44-08+ `qjpa` codemod safety:** Per RESEARCH.md §10.3 open question 5
   — does the project have sufficient test coverage to validate a 461-file
   codemod? If not, the plan should land behind a feature flag. The
   executor must check `pnpm test` coverage thresholds during planning.
