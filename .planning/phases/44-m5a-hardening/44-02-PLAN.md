# Plan 44-02: Observability Decision Document + OPS Runbook for the 7-Day M5b Soak

## Goal

Author the canonical observability decision document (`.planning/observability-soak-M5.md`) and the operational runbook (`docs/STEERING/OBSERVABILITY.md`) that ratify the Pino + Sentry + `@vercel/otel` stack documented in `44-RESEARCH.md` §3 and specify the 7-day soak signal set, alert thresholds, PII scrubbing rules, and on-call escalation paths. The M5b launch team uses both documents as the source of truth for the 7-day soak that begins Phase 45.

## Why this plan exists

`44-CONTEXT.md` lists "monitoring infrastructure planning (NEW — Plan 44-02 TBD)" as a Phase 44 acceptance criterion: "`.planning/observability-soak-M5.md` documents the monitoring stack for the 7-day soak." The 7-day production soak was repositioned to **M5b Launch (Phase 45)** on 2026-06-07 because it is a launch verification, not a production-readiness deliverable. Before the soak can begin, the team must agree on:

1. **Stack shape** — what observability tools will we use? Pino is already in the repo; the question is whether we add Sentry, `@vercel/otel`, or both. RESEARCH.md §3.2 recommends Pino (extend) + Sentry (new) + `@vercel/otel` (new).
2. **Signal set** — what are we watching during the soak? 7 SLOs in RESEARCH §3.4 (server TTFB, error rate, client JS errors, LCP, Pino log rate, chat delivery, Sentry backlog). Each needs a target and an alert threshold.
3. **PII handling** — chat messages, email addresses, and property details flow through the system. Sentry and OTel are third-party SaaS. RESEARCH §3.6 calls out PII scrubbing as a GDPR/POPIA-blocking risk.
4. **Abort criteria** — what makes the soak fail? The M4.5 criteria in `.planning/MILESTONES.md` §2.6 say "zero P0/P1 incidents" but the team needs concrete signal-to-decision rules.
5. **Open questions** — RESEARCH §10.3 lists 5 open questions, 2 of which (Sentry org, Vercel plan tier) block the actual code-installation work and are therefore answerable in this plan.

This plan is a **documentation deliverable, not a code deliverable**. The Sentry install + `@vercel/otel` wiring is a separate code plan (44-02b) that depends on the user ratifying the decisions in the 44-02 docs. This sequencing matters: shipping the doc first means the code plan can proceed without re-asking the strategic questions, and the M5b launch team has a written record of the decision rationale.

## Scope

**In scope:**

- `.planning/observability-soak-M5.md` — the decision document. Stack, capability map, signal set, alert thresholds, PII scrubbing rules, soak start/stop/abort criteria, on-call escalation, open questions with status.
- `docs/STEERING/OBSERVABILITY.md` — the OPS runbook. Sentry dashboard tour (per issue triage), Vercel Web Vitals / Monitoring dashboard tour, Pino log query cheatsheet (Vercel Logs + Log Drains if Pro), common alerts and their runbook links.

**Out of scope (deferred to a follow-up 44-02b code plan):**

- `pnpm add @sentry/nextjs @vercel/otel @opentelemetry/api` — depends on Sentry org decision
- `instrumentation.ts` + `sentry.{server,edge,client}.config.ts` — depends on env vars (DSN, ORG, PROJECT, AUTH_TOKEN)
- `withTiming` Sentry span wiring (additive ~20 lines in `src/shared/api/observability.ts`) — depends on Sentry init
- Sentry breadcrumb calls in `apiLogger` + `authLogger` — depends on Sentry init
- Vercel Log Drain configuration (if Pro plan ratified) — depends on Vercel plan tier decision
- The 4 unit tests in RESEARCH §3.8 (OBS-01..OBS-04) — depend on Sentry init code

**Why the split matters:** 44-RESEARCH.md recommends shipping Sentry + `@vercel/otel` *before* the `qjpa` codemod in 44-10 because the 461-file codemod is the highest-risk item in the phase. We want the safety net in place before we start touching files at scale. The 44-02 docs are the prerequisite; the 44-02b code is the safety net. Sequencing is documented in the M5b hand-off section of the decision doc.

## Open questions for the human-verify checkpoint

These are the strategic decisions the user must ratify in Task 3. Each maps to an open question in 44-RESEARCH.md §10.3 and a section in the decision doc:

1. **Sentry org setup** — does the project already have a Sentry org, or does one need to be created? If created, who owns the org billing? (Blocks 44-02b kickoff.)
2. **Vercel plan tier** — Hobby, Pro, or Enterprise? Log Drains + Vercel Monitoring depth depend on this. If Hobby, the soak signal set is reduced (no log drain for long-term retention; no Vercel Monitoring 5xx view). (Impacts 44-02b env-var block.)
3. **Abort criteria for the soak** — does "zero P0/P1 incidents" mean zero P1 incidents in a 24-hour window, or zero for the full 7 days? P2/P3 tolerance? (Impacts the M5b hand-off in MILESTONES.md.)
4. **On-call rotation** — single owner for 7 days, or shared? PagerDuty, Slack, or both? (Impacts the runbook's escalation path.)
5. **PII scrubbing scope** — chat message bodies, email addresses, property addresses, or all of the above? The decision doc proposes a default of "scrub chat bodies + email + property address"; the user can ratify or expand.

## Threat model (ASVS L1)

This plan introduces **no new endpoints, no schema changes, and no new dependencies**. The threat model covers the observability stack the docs recommend (Sentry + OTel + Pino drain) — the threats and mitigations are documented in the decision doc itself, so the M5b team can apply them when 44-02b lands.

| Trust boundary | What crosses it | Threat | Disposition | Mitigation (documented in `.planning/observability-soak-M5.md` §5) |
|----------------|-----------------|--------|-------------|--------------------------------------------------------------|
| Browser → Sentry SaaS | Unhandled exceptions, breadcrumbs, session replays | PII leakage via stack-trace payloads (chat bodies, emails) | mitigate | `sendDefaultPii: false` in `Sentry.init()`; `beforeSend` scrubber for `user.email`, `body.content`, `property.address`; disable Session Replay by default in 44-02b |
| API route → Sentry SaaS | `withTiming` spans, error captures from `apiLogger` | PII leakage via log context (tenantId correlation OK; chat bodies not) | mitigate | `beforeSend` strips `breadcrumb.data.body` for `/api/messages/*` and `/api/chat/*` |
| API route → Vercel Logs | Pino JSON lines | Log volume cost overruns on Vercel Pro | mitigate | Pino `level: 'info'` in production (already configured in `src/shared/lib/logger.ts`); Log Drain targets a single aggregator with 30-day retention |
| App → `@vercel/otel` collector → Sentry | OTel spans, request/response metadata | Latency overhead from OTel SDK in hot paths (chat, notifications) | mitigate | `tracesSampleRate: 0.1` (10% sample) for Sentry perf; 100% for errors; benchmark in staging before 44-02b ships |
| Vercel Logs → Log Drain aggregator | Pino JSON, Vercel Web Vitals metrics | PII leakage to third-party aggregator (Datadog, Better Stack, etc.) | mitigate | Pino redact list for `req.headers.authorization`, `req.headers.cookie`, `user.email`; Vercel Log Drain URL kept in env vars, not committed |
| Sentry dashboard → user PII | Issue details, stack traces, breadcrumbs | Unauthorised user sees tenant data in Sentry | mitigate | Sentry org RBAC: tenant data lives in `tags.tenantId`; Sentry users granted access by role (admin / developer / observer) with least-privilege perms |
| Soak alerting → on-call channel | PagerDuty / Slack notification with Sentry link | PII leakage in alert text (Sentry issue title may contain a chat snippet) | mitigate | Sentry alert template uses `{{ issue.title }}` only, not body; PagerDuty description renders issue ID, not payload |
| `.planning/observability-soak-M5.md` → public read | Decision rationale, SLOs, runbook pointer | Document leaks Sentry org name / DSN / PagerDuty URL | mitigate | Decision doc declares Sentry org, DSN, and PagerDuty URL as **placeholders** (e.g., `$SENTRY_ORG`); actual values live in `.env` and Sentry dashboard access is RBAC-gated |

No high-severity threats block the plan. All mitigations are documented in the decision doc as recommendations; 44-02b enforces them at the code level.
