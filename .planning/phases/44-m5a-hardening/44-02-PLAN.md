# Plan 44-02: PostHog Observability Stack + Soak Decision Doc

## Goal

Ratify the Pino + PostHog observability stack for the 7-day M5b soak. Author the decision document (`.planning/observability-soak-M5.md`), the operational runbook (`docs/STEERING/OBSERVABILITY.md`), and wire PostHog into the application via `instrumentation-client.ts` (Next.js 15.3+ lightweight pattern) and `layout.tsx`. The M5b launch team uses the decision doc as the strategic reference and the runbook as their on-the-job reference during the soak.

## Why this plan exists

`44-CONTEXT.md` lists "monitoring infrastructure planning (NEW — Plan 44-02 TBD)" as a Phase 44 acceptance criterion. The 7-day production soak was repositioned to **M5b Launch (Phase 45)** on 2026-06-07 because it is a launch verification, not a production-readiness deliverable. Before the soak can begin, the team must:

1. **Ratify the stack** — Pino (existing) + PostHog (new). PostHog replaces Sentry + `@vercel/otel` from the original `44-RESEARCH.md` §3 research, based on the team's preference for an all-in-one product analytics + session recording + feature flag platform with a simpler setup footprint.
2. **Instrument client-side observability** — PostHog captures pageviews, autocapture (clicks, navigation, form interactions), and errors. The `instrumentation-client.ts` pattern loads before React hydration (Next.js 15.3+), so no events are missed during the initial render.
3. **Set signal set** — what are we watching during the soak? SLO targets, alert thresholds, and on-call actions for each.
4. **Document PII scrubbing** — autocapture captures DOM text by default. The plan defines a redact/ignore strategy so chat messages, email addresses, and property details never leave the browser.
5. **Define abort criteria** — what makes the soak fail?

## Scope

**In scope:**

- `.planning/observability-soak-M5.md` — decision document. Stack (Pino + PostHog), capability map, signal set, PII scrubbing, soak start/stop/abort criteria, on-call escalation.
- `docs/STEERING/OBSERVABILITY.md` — OPS runbook. PostHog dashboard tour, Vercel Web Vitals / Monitoring tour, Pino log query cheatsheet, common alerts and their first-action runbook steps, soak abort procedure.
- `src/instrumentation-client.ts` — PostHog initialisation with defaults `'2026-01-30'`, `api_host: '/ingest'` (reverse proxy), autocapture enabled, `capture_pageview: true` (pageview tracking handled by PostHogPageView component), `session_recording` with privacy masking (`maskAllInputs: true`, `maskTextSelector: '*'`).
- `src/app/layout.tsx` — wrap with `PostHogProvider` from `@posthog/next`, add `PostHogPageView` inside `<Suspense fallback={null}>`.

**Out of scope:**
- PostHog feature flags — available via PostHogProvider `bootstrapFlags` but not configured yet; deferred to a future BV issue if needed
- PostHog group analytics (tenant-level analysis) — deferred; the plan captures `tenantId` as a person property if available
- Supabase Realtime monitoring — already handled by existing Pino logging in realtime routes
- Production data migration scripts or schema changes (no Prisma/Drizzle/Supabase schema work)
- **UI-SPEC.md D4 (Observability Surfaces) is superseded** — D4 was written for the Sentry + @vercel/otel stack. This plan's decision doc and runbook replace it. The UI-SPEC.md itself is NOT being modified; the D4 sections should be treated as out-of-date and the decision doc is the new source of truth.

## Threat model (ASVS L1)

This plan introduces PostHog client-side SDK (`posthog-js`) and a reverse-proxy endpoint (`/ingest`). It does not add schema changes or new server-side endpoints beyond the reverse-proxy rewrite.

| Trust boundary | What crosses it | Threat | Disposition | Mitigation |
|----------------|-----------------|--------|-------------|------------|
| Browser → PostHog cloud (via reverse proxy) | Autocapture events, pageviews, session recordings | PII leakage via autocaptured DOM text (chat messages, email addresses, property details) | mitigate | `maskAllInputs: true` in `posthog.init()`; CSS class `.ph-no-capture` on sensitive elements; `maskTextSelector: '*'` to mask all text by default and opt in per-element |
| Browser → `api_host: '/ingest'` (same-origin proxy) | Captured event payloads | Reverse-proxy misconfiguration sends data to wrong host | mitigate | PostHogHost must match the project's PostHog instance; verify `NEXT_PUBLIC_POSTHOG_HOST` matches the configured reverse-proxy upstream |
| PostHog dashboard → user | Event properties, session recordings, user properties | Unauthorised user sees tenant-level analytics in PostHog | mitigate | PostHog project RBAC: invite only developers + ops team; do not share dashboard links externally |
| Soak alerting → on-call channel | Slack/PagerDuty notification with PostHog insight link | PII leakage in alert text (insight may include a user email or property name) | mitigate | Configure PostHog action alerts with `$event_type` only, not person properties; alert templates use event names, not property values |
| Third-party CDN scripts (`eu.posthog.com`) | PostHog SDK loaded from PostHog CDN | CDN compromise could inject malicious JS | mitigate | Reverse proxy (`/ingest` + loaded via the same domain) eliminates CDN dependency for script loading; use `instrumentation-client.ts` which loads from the installed npm package, not a CDN |

No high-severity threats block the plan. All mitigations are code-level (implemented in Tasks 3-4) and documented in the decision doc §5.
