<objective>
Transform `POST /api/platform/tenants` from a public, identity-creating endpoint into an authenticated, tenant-creating-only endpoint. The caller must have a verified session; the route creates only the tenant, sets `user.tenantId` + role, and runs `initTenantSetup()`. No user creation, no orphan risk.

Purpose: Move tenant provisioning behind the auth wall so only verified identities can create communities. Eliminate failure modes F1 (zombie tenants) and F2 (slug squatting).

Output: Authenticated, session-required `POST /api/platform/tenants` endpoint with verified-email guard. TDD plan — RED (failing tests) → GREEN (implementation) cycle.
</objective>

<threat_model>

## Trust Boundaries

| Boundary                          | Description                                                                                                                            |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Client→POST /api/platform/tenants | Previously public; now requires authenticated session. Session token is the trust boundary — unauthenticated requests rejected at 401. |
| Verified session→tenant creation  | `session.user.emailVerified` must be true. Unverified users cannot provision (prevents zombie tenants from throwaway emails).          |

## STRIDE Threat Register

| Threat ID   | Category               | Component                                          | Severity | Disposition | Mitigation Plan                                                                                                                                                                                         |
| ----------- | ---------------------- | -------------------------------------------------- | -------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T-124-05-01 | Spoofing               | `auth.api.getSession()` — session forgery          | high     | mitigate    | Better Auth validates the session token cryptographically. No custom token parsing. The `emailVerified` check adds defense-in-depth: even a valid session must have a verified email.                   |
| T-124-05-02 | Tampering              | `POST /api/platform/tenants` body (slug injection) | medium   | mitigate    | Zod schema validates `slug` against regex `^[a-z0-9](?:[a-z0-9-]*[a-z0-9])?$`. Slug uniqueness is checked against live table. DB unique constraint on `tenants.slug` is the backstop.                   |
| T-124-05-03 | Repudiation            | Tenant creation without audit trail                | low      | accept      | No audit table exists for tenant creation. The Tenant row itself (with `createdAt`) serves as the creation record. This is a pre-existing gap, not introduced by this phase.                            |
| T-124-05-04 | Elevation of Privilege | `role=ADMIN` assignment                            | medium   | mitigate    | The creating user is assigned `ADMIN` role on their own tenant — this is by design (community creator = admin). No escalation path exists because the user had no tenant access before creation.        |
| T-124-05-05 | Denial of Service      | Slug squatting via authenticated retry             | low      | accept      | Slug conflicts (409) are retryable by the authenticated user. The user can choose a different slug. This is intentional — no reservation or TTL needed (ADVISORY-031 Option C, "defer, don't reserve"). |
| T-124-05-SC | Tampering              | npm/pnpm installs                                  | high     | mitigate    | No new packages. RESEARCH.md Package Legitimacy Audit confirms all dependencies are installed and verified.                                                                                             |

</threat_model>
