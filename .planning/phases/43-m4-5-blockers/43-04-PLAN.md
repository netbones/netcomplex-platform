<objective>
Refactor the 5 admin API route handlers (`/api/admin/activity`, `/api/admin/board-members`, `/api/admin/maintenance-stats`, `/api/admin/urgency`, `/api/admin/settings/page-flags`) to execute inside a `runWithRLS(ctx, async (tx) => ...)` transaction. This sets the Postgres session-local RLS context (`app.tenant_id`, `app.user_id`, `app.user_role`, `app.is_platform_admin`) and the `app_user` PG role BEFORE any query touches a tenant-scoped table, so that RLS policies (defined in `prisma/migrations/.../rls-policies.sql`) are enforced at the database layer.

Purpose: BD issue `oqw` (P2) — defense-in-depth for the 5 admin routes identified by the audit. Today, these routes filter on `tenantId` in the WHERE clause (via `withTenant()`), but the filtering is application-level. A bug in a future refactor could drop the WHERE clause and leak cross-tenant data. Wrapping in `runWithRLS` adds a database-level guarantee: even if a future bug drops the WHERE clause, RLS policies block the query at the DB layer.

Output: 5 modified route files. The 5 routes are still 200 OK, still return the same data, but now execute under the `app_user` PG role with RLS context set. The audit's "PASS" status for these routes is now backed by the database, not just the application code.
</objective>

```typescript
export type RLSContext = {
  userId: string;
  tenantId: string;
  role: string;
  isPlatformAdmin: boolean;
};

// runWithRLS signature (lines 189-203)
export async function runWithRLS<T>(
  ctx: RLSContext,
  fn: (tx: NodePgDatabase<DbSchema>) => Promise<T>
): Promise<T> {
  return getDb().transaction(async tx => {
    await tx.execute(sql`SET ROLE app_user`);
    await tx.execute(sql`SELECT set_config('app.user_id', ${ctx.userId}, true)`);
    await tx.execute(sql`SELECT set_config('app.tenant_id', ${ctx.tenantId}, true)`);
    await tx.execute(sql`SELECT set_config('app.user_role', ${ctx.role}, true)`);
    await tx.execute(
      sql`SELECT set_config('app.is_platform_admin', ${ctx.isPlatformAdmin ? 'true' : 'false'}, true)`
    );
    return fn(tx as unknown as NodePgDatabase<DbSchema>);
  });
}

// getRLSContext signature (lines 209-224)
export async function getRLSContext(request: Request): Promise<RLSContext | null> {
  const { auth } = await import('@api/auth');
  const session = await auth.api.getSession({ headers: request.headers });
  if (!session?.user?.id) return null;
  const [user] = await db.select().from(users).where(eq(users.id, session.user.id)).limit(1);
  if (!user) return null;
  return {
    userId: user.id,
    tenantId: user.tenantId,
    role: user.role,
    isPlatformAdmin: user.isPlatformAdmin,
  };
}
```

Refactor pattern (apply to all 5 routes):

```typescript
// BEFORE
export async function GET(request: NextRequest) {
  const authError = await requireAnyPermission(['admin', 'settings']);
  if (authError) return authError;
  const { tenantId } = await withTenant();
  const items = await db.select(...).from(table).where(...);
  return apiSuccess(items);
}

// AFTER
export async function GET(request: NextRequest) {
  const authError = await requireAnyPermission(['admin', 'settings']);
  if (authError) return authError;
  const ctx = await getRLSContext(request);
  if (!ctx) return apiUnauthorized();
  return runWithRLS(ctx, async (tx) => {
    const { tenantId } = await withTenant();
    const items = await tx.select(...).from(table).where(...);
    return apiSuccess(items);
  });
}
```

- Routes that delegate to a helper function (e.g., `page-flags/route.ts` calls `getPlatformPageFlags(tenantId)` which internally does `db.select`) MUST either: (a) refactor the helper to accept `tx` and call it with `tx`, or (b) accept that the helper still uses the global `db` (which has the `app_user` role from the SET LOCAL outside the helper... NO, this doesn't work — the `SET ROLE app_user` is scoped to the transaction, not visible to a different `db` connection). Option (a) is required: refactor the helper to accept `tx`.

## Trust Boundaries

| Boundary                                          | Description                                                                                                                                                                                                                      |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unauthenticated user → admin route                | Today, the `requireAnyPermission` / `getSessionAndRole` / `isAdmin` check is the ONLY line of defense. If it returns `null` or is bypassed, the route proceeds to `db.select` queries.                                           |
| Authenticated user → admin route                  | The user has a session and a tenant. The `withTenant()` helper filters queries by `tenantId` in the application code. If a future refactor drops the `tenantId` WHERE clause, the query returns cross-tenant data.               |
| Authenticated user → DB (no RLS)                  | The DB connection uses the `postgres` superuser role by default. RLS policies are NOT enforced because the role has BYPASSRLS. A bug in the application code OR a SQL injection could leak data.                                 |
| Authenticated user → DB (with RLS via runWithRLS) | The DB connection uses the `app_user` role (set via `SET LOCAL app_user` inside the transaction). RLS policies ARE enforced; the query can only see rows where the policy evaluates true for `current_setting('app.tenant_id')`. |
