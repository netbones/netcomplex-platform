# Plan 01: Provider Dashboard Space, Analytics & Verified Status

## Objective

Create a dedicated "Providers" dashboard space with provider-scoped analytics, a provider-facing dashboard, and **verified/unverified status indicators**. This plan covers provider analytics (kia), provider dashboard (9e8), and the **verification status system** which gates provider capabilities based on community trust.

## must_haves

- [ ] Provider can view a dedicated dashboard space with analytics widgets
- [ ] Provider analytics are scoped to their listings only (not admin-wide)
- [ ] **Provider's verification status (verified/unverified/probation) is prominently displayed**
- [ ] **Verified providers have full analytics; unverified providers see limited/probationary data**
- [ ] Dashboard space is gated behind `providers` permission
- [ ] Analytics include: listing views, inquiry counts, review summary, community credit score
- [ ] Provider dashboard shows active listings, inquiries, performance stats, and credit progress toward verification

## Background

The codebase has a dashboard space architecture (`spaces.ts`, `widgets.ts`) and an existing admin-only analytics route at `/api/community-services/analytics`. This plan adds a new `providers` space and provider-scoped analytics. The existing `ServiceProvider` and `CommunityServiceListing` tables provide the data model.

**Key decision from research (Assumption A3):** `CommunityServiceListing.providerId` equals `users.id` (the provider's user ID), NOT `serviceProviders.id`. Dashboard queries must filter by `session.user.id`.

### Wave 1: Verification System

- Provider status types: UNVERIFIED, PROBATION, VERIFIED, SUSPENDED

- Verification status is returned in `/api/providers/verification` and cached client-side
- Status display: red (UNVERIFIED), yellow (PROBATION), green (VERIFIED), red (SUSPENDED)
  </acceptance_criteria>

1. Create `src/db/schema/provider-verification.ts`
   - id, providerId, tenantId, status (enum: UNVERIFIED, PROBATION, VERIFIED, SUSPENDED), startDate, endDate, notes, createdAt, updatedAt
   - FK: providerId → serviceProviders.id, tenantId → tenant.id
2. Create endpoint: `GET /api/providers/verification`
   - Fetch from providerVerification for current provider
   - If no record exists, return default: PROBATION for new providers
3. Create endpoint: `PATCH /api/providers/verification` (admin only)
   - Allows admin to update verification status
4. Create endpoint: `GET /api/providers/analytics/credit-score` (calculates community credit score for providers)
   - Calculates community credits based on service quality, response time, compliance history
</action>
</task>
