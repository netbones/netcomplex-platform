**GAP-10: AssistSession scope enforcement**

1. Create `src/entities/tenant/api/assist-scope-guard.ts`:
   - Export `requireAssistScope(request, requiredScope: 'full' | 'metadata')` function
   - This function checks if the requesting user is operating under an active assist session
   - How it works:
     a. Get session from `auth.api.getSession()`
     b. Query the user's active assist sessions: `SELECT * FROM assistSessions WHERE staffId = userId AND isActive = true AND expiresAt > now()`
     c. If any session exists with `scope = 'metadata'` AND the requiredScope is 'full': return 403
     d. If no active assist session: the user is a regular user, allow (return null = no restriction)
     e. If session scope = 'full': allow everything (return null = no restriction)
     f. If session scope = 'metadata' AND requiredScope = 'metadata': allow (return null)
   - Usage: API routes that handle content, users, or settings should call `requireAssistScope(request, 'full')` and if it returns a 403 response, return that response immediately

2. Apply the guard to sensitive API routes:

- `src/app/api/content/route.ts`: Add `requireAssistScope(request, 'full')` check before POST/PATCH/DELETE operations
- `src/app/api/users/[id]/route.ts`: Add `requireAssistScope(request, 'full')` check before PATCH/DELETE
- `src/app/api/settings/[key]/route.ts` (created by Plan 01): Add `requireAssistScope(request, 'full')` check before PATCH
- Do NOT add the guard to read-only GET routes — metadata scope should be able to read everything
- Add a comment: `// AssistSession scope guard: metadata-scoped staff can only read, not modify content/users/settings`

**GAP-13: Widget state DB sync**
