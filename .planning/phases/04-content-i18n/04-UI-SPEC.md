## Phase-Specific Constraints

### No New UI Surfaces

This phase does NOT introduce:

- New pages, components, modals, or widgets
- New forms, buttons, or interactive elements
- New loading states, empty states, or error states
- New navigation items
- New color, typography, or spacing overrides

### What This Phase Does Touch

These existing UI surfaces are touched, but only to change their data-fetching logic (not their visual appearance):

| Surface                    | Change                                          | Visual Impact                                               |
| -------------------------- | ----------------------------------------------- | ----------------------------------------------------------- |
| `/news` page               | Add `&locale=${i18n.language}` to content fetch | None — content renders same cards with locale-resolved text |
| `/news/[id]` page          | Add `&locale=${i18n.language}` to content fetch | None                                                        |
| `ServicesPage`             | Add `&locale=${language}` to content fetch      | None                                                        |
| `/resident/[id]` page      | Add `&locale=${i18n.language}` to content fetch | None                                                        |
| `/unit/[id]` page          | Add `&locale=` to content fetch                 | None                                                        |
| `UserContentWidget`        | Add `&locale=${language}` to content fetch      | None                                                        |
| `TagCloudWidget`           | Add `&locale=${language}` to content fetch      | None                                                        |
| `/admin/content` page      | Add `&locale=` to content fetch                 | None                                                        |
| `HomeLayer` (resolveTitle) | Replace hardcoded `'en'` with `i18n.language`   | Content titles render in user's locale                      |
| `/conservation` page       | Remove redundant `getLocalizedContent()` helper | None — API already returns flat strings                     |

### Interaction Contract

- **Locale switching:** When the user changes language via `LanguageSwitcher`, content must re-fetch with the new locale. This is achieved by including `language` in `useEffect` dependency arrays.
- **Fallback behavior:** The API already handles missing locale keys via `getLocalizedValue()` fallback chain. Client code must not duplicate this logic.
- **Admin editing:** The `_raw` JSONB field in API responses must be preserved. Client code removing `getLocalizedContent()` helpers must not affect admin content editing pages that read `content._raw.title`.

**Source:** RESEARCH.md §Content Display Audit + §Redundant Client-Side Locale Helpers.
