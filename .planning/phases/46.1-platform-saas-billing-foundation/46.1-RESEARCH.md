# Phase 46.1: Platform SaaS Billing Foundation - Research

**Researched:** 2026-06-25
**Domain:** Multi-tenant SaaS billing (subscription lifecycle, checkout, invoicing, payment processing)
**Confidence:** HIGH

## Summary

Phase 46.1 extends the provider billing infrastructure delivered in Phase 46 (plans 46-01 through 46-04) to establish platform-level SaaS billing for tenants. The codebase already has a working payment gateway abstraction (Paystack + PayPal), a proven checkout/cancellation/refund lifecycle in `src/shared/api/provider-billing.ts` (1375 lines), and a Drizzle-based billing data model with subscription tiers, payment transactions, invoices, charges, and revenue records. Phase 46.1 reuses these patterns wholesale — the same gateways, the same `apiSuccess`/`apiError` envelope, the same `ProviderBillingActionResult<T>` pattern, the same `ensureXxxRecord` upsert approach, and the same `requirePlatformAdmin` / `requireAnyPermission` guard conventions. The primary difference is the domain: tenant SaaS billing replaces provider marketplace billing.

The critical architectural step is, per CONTEXT.md, piping `BillingPlan → TenantSubscription → Tenant.tier` so that the `Tier` enum column on `Tenant` becomes the output of a subscription system rather than a manually-assigned field. This transition must preserve backward compatibility with Phase 104's `getTierQuota()` (which reads `tenants.tier` directly — no code changes needed in Phase 104; per CONTEXT.md §Specifics).

**Primary recommendation:** Clone the Phase 46 provider billing patterns for tenant billing — new Prisma models mirroring `ProviderSubscription`/`PaymentTransaction`/`ProviderInvoice` structure, new Drizzle schema files, new `src/shared/api/tenant-billing.ts` following `provider-billing.ts` conventions, new platform admin routes under `/api/admin/platform/billing/`, new admin widgets registered in `widgets.ts`, and a new tenant portal under `/tenant/billing`. Defer PDF generation and coupon/tax engine depth to agent discretion. Keep `Tenant.tier` as a manual fallback during transition — set it from subscription lifecycle but allow admin override for migration safety.

### Pattern 1: Billing Action Result (from Phase 46)

**What:** Union type for all billing operations — `ok: true` with data or `ok: false` with status/message. Used by checkout, cancel, refund, and tier transition.

**When to use:** Every billing mutation function that can fail for business-logic reasons (not found, insufficient permissions, gateway down).

**Example:**

```typescript
// Source: src/shared/api/provider-billing.ts lines 30-43 [VERIFIED: codebase]
export interface TenantBillingActionError {
  ok: false;
  status: number;
  message: string;
}

export interface TenantBillingActionSuccess<T> {
  ok: true;
  data: T;
}

export type TenantBillingActionResult<T> = TenantBillingActionError | TenantBillingActionSuccess<T>;
```

### Pattern 2: Ensure-Record Upsert (from Phase 46)

**What:** Functions that check for existing records before inserting, returning the existing or newly-created row. Used for invoices, charges, and revenue records.

**When to use:** Webhook handlers and transaction-completion flows where the same gateway callback may fire multiple times (idempotency).

**Example:**

```typescript
// Source: src/shared/api/provider-billing.ts lines 261-310 [VERIFIED: codebase]

    .from(tenantInvoices)
    .where(eq(tenantInvoices.transactionId, params.transaction.id))

    // update and return
  }
  // insert and return
}
```

### Pattern 4: Subscription Checkout Lifecycle (from Phase 46)

**What:** Create subscription (PENDING/ACTIVE) → initialize gateway payment → store transaction → webhook callback marks completed → update subscription to ACTIVE.

**When to use:** Tenant plan selection and payment flow. For free plans (price=0): skip gateway, insert COMPLETED transaction directly.

**Example (psuedocode — see provider-billing.ts lines 628-908 for full 280-line implementation):**

```typescript

// 1. Validate tier exists and is allowed for tenant
// 2. Cancel any existing ACTIVE/PENDING subscriptions
// 3. If price=0: insert ACTIVE subscription + COMPLETED transaction + invoice + revenue
// 4. If price>0: insert PENDING subscription + gateway checkout
// 5. Gateway webhook → markTransactionCompletedByReference → ACTIVE subscription
```

### Anti-Patterns to Avoid

- **Mixing tenant and provider billing tables:** Do NOT reuse `PaymentTransaction` for tenant payments. The schemas have different relationships (tenant vs provider FK), different lifecycle states, and different query patterns. Separate tables avoid polymorphic joins and permission confusion.
- **Direct `Tenant.tier` writes scattered across codebase:** All tier derivation must go through a single `syncTierToTenant(tenantId)` function called from subscription lifecycle handlers. Manual admin overrides should also use this function to maintain audit trail.
- **Baking tax rates into invoice line items:** Per CONTEXT.md, use `TaxRate` and `TaxJurisdiction` configuration tables. Tax rates change — hardcoded values in invoices break on rate changes.
- **Skipping the BillingEvent stream:** Every state transition (SUBSCRIPTION_CREATED, PAYMENT_RECEIVED, etc.) must emit an immutable BillingEvent. Without this, support and audit have no source of truth for "what happened when."
- **Gateway webhooks without idempotency:** Paystack/PayPal may send the same webhook multiple times. All webhook handlers must use the ensure-record pattern.

## Common Pitfalls

### Pitfall 1: Breaking Phase 104 AI Pool Quota Lookup

**What goes wrong:** `getTierQuota()` reads `tenants.tier` directly. If Phase 46.1 changes the column type, adds a NOT NULL constraint violation, or introduces a race condition where `tier` is briefly null during subscription transitions, AI pool quota checks fail.

**Why it happens:** The tier column is read synchronously in `resolveGateContext()` → `canAccess()` for every feature gate check. Any interruption in the tier derivation pipeline causes a cascading gate failure.

**How to avoid:** Never set `Tenant.tier` to null. The `syncTierToTenant()` function must always write a valid Tier value. Keep the `@default(STANDARD)` on the column as a safety net. Test that Phase 104's `getTierQuota()` returns correct values after subscription creation, upgrade, downgrade, cancellation, and payment failure.

**Warning signs:** AI pool route returns 500 with "Tenant tier not found" or returns wrong quota.

### Pitfall 2: Webhook Race Conditions

**What goes wrong:** Paystack/PayPal webhook fires before the checkout page has fully created the subscription in the DB, causing `markTransactionCompletedByReference` to return 404.

**Why it happens:** Gateway webhooks are asynchronous and can arrive within seconds. If the HTTP response from `initializeGatewayCheckout` is slow, the webhook may beat the DB write.

**How to avoid:** Use the ensure-record pattern (check existing, create if missing) in webhook handlers. The subscription is created in a `db.transaction()` before the gateway is called — guaranteeing the record exists before the redirect URL is returned.

### Pitfall 3: Tenant.tier Drift After Manual Admin Override

**What goes wrong:** Platform admin manually changes `Tenant.tier` via admin route, but a subsequent subscription renewal overwrites it. Admin expects their manual change to persist.

**Why it happens:** Two sources of truth for the same column (manual admin assignment + automated subscription derivation) without clear precedence.

**How to avoid:** Per CONTEXT.md agent discretion: keep manual assignment as a fallback. The `syncTierToTenant()` function should only update `tier` when the subscription is ACTIVE. If admin manually sets tier via a separate route, add a `tierManualOverride` flag on Tenant to prevent subscription lifecycle from overwriting. This avoids the "admin changes tier, subscription reverts it" loop.

### Pitfall 4: Duplicate Subscription Creation

**What goes wrong:** Tenant clicks "Subscribe" twice, creating two PENDING subscriptions and charging the tenant twice.

**Why it happens:** No check for existing ACTIVE/PENDING subscriptions before creating a new one.

**How to avoid:** Reuse Phase 46's pattern — `createProviderSubscriptionCheckout()` cancels all existing ACTIVE/PENDING subscriptions before creating a new one (lines 679-704 in `provider-billing.ts`). Tenant billing must do the same.

## Open Questions

1. **Should the `billing` feature module be gated behind a `canAccess('page.billing')` or a new permission key?**
   - What we know: Phase 46 uses `requireAnyPermission(['providers'])` for provider billing. Platform admin routes use `requirePlatformAdmin`. Tenant billing portal will need a different gate (tenant-facing, not admin).
   - What's unclear: Whether to create a new `billing` permission in `ROLE_PERMISSIONS` or reuse an existing permission. New permission adds complexity but is cleaner semantically.
   - Recommendation: Add `billing: true` to `ROLE_PERMISSIONS` for all roles (every tenant can see their own billing). Use `withTenant()` for tenant isolation. Platform admin billing routes use `requirePlatformAdmin`.

2. **Should tenant subscriptions use Stripe's subscription API instead of Paystack/PayPal one-time charges?**
   - What we know: Phase 46 uses one-time checkout charges (not recurring subscriptions) for provider billing. Paystack supports recurring plans, but the codebase doesn't use them yet.
   - What's unclear: Whether Phase 46.1 needs true recurring billing (auto-charge on renewal date) or manual renewal (tenant re-checks out each month).
   - Recommendation: Start with manual renewal (one-time checkout per billing cycle, with `nextBillingDate` prompting the tenant). True recurring billing requires gateway subscription API integration — defer to a follow-up phase.

3. **Where should the BillingPlan seed data live — in a migration or in `scripts/seed-drizzle.ts`?**
   - What we know: Phase 46 seeds default provider tiers in `provider-billing.ts` `getOrCreateDefaultSubscriptionTiers()`. Seed data runs in `scripts/seed-drizzle.ts`.
   - What's unclear: Whether billing plans should be seeded in the migration (always present in DB) or in the seed script (dev/test only).
   - Recommendation: Seed in both — migration adds STANDARD/PREMIUM/ENTERPRISE plans as defaults, seed script ensures they exist for dev databases. Use the `getOrCreate` pattern from Phase 46.

| V7 Error Handling     | yes            | `logError` for all catch blocks; never expose gateway secrets in error messages                                             |
| V8 Data Protection    | yes            | Financial data (payment amounts, invoice totals) must be immutable after creation; BillingEvent stream provides audit trail |

### Known Threat Patterns for Next.js + Drizzle + Payment Gateways

| Pattern                                    | STRIDE                 | Standard Mitigation                                                                                       |
| ------------------------------------------ | ---------------------- | --------------------------------------------------------------------------------------------------------- |
| Webhook replay attack                      | Spoofing               | Paystack HMAC signature verification; PayPal webhook-signature API. Both already implemented in Phase 46. |
| Tenant A accessing Tenant B's subscription | Information Disclosure | `withTenant()` ensures `tenantId` filter on all Drizzle queries                                           |
| Price manipulation in checkout             | Tampering              | Server-side price lookup from `BillingPlan` table — never trust client-supplied price                     |
| Double-charge on duplicate checkout        | Denial of Service      | Cancel existing PENDING subscriptions before creating new one (Phase 46 pattern)                          |
| Admin mass-refund abuse                    | Elevation of Privilege | `requirePlatformAdmin` guard + `writeAuditLog` on every refund                                            |
| Subscription status race condition         | Tampering              | `db.transaction()` wraps all multi-table writes in subscription lifecycle                                 |
