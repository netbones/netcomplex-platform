**Step 2 — Gateway configuration helper** (lines 21-35):

**Step 3 — createTenantSubscriptionCheckout** (main checkout function, ~250 lines):
Parameters: `{ tenantId, planId, paymentGateway, billingEmail, callbackUrl?, couponCode? }`
Returns: `Promise<TenantBillingActionResult<{ subscriptionId, transactionId, status, paymentUrl, reference }>>`

Logic (following provider-billing.ts lines 628-908):

1. Validate plan exists and isActive — if not, return error 404
2. Validate paymentGateway is configured (for paid plans) — if not, return error with status 503 and message "Payment processing is not yet configured"
3. If couponCode provided: validate coupon exists, is active, not expired, maxRedemptions not reached; store couponId for later application
4. Cancel any existing ACTIVE/PENDING/TRIALING subscriptions for this tenant: `db.update(tenantSubscriptions).set({ status: 'CANCELLED', cancelledAt: now() }).where(and(eq(tenantSubscriptions.tenantId, tenantId), inArray(tenantSubscriptions.status, ['ACTIVE', 'PENDING', 'TRIALING'])))`
5. Calculate billing amount: use monthlyPrice or annualPrice based on plan.interval. Apply coupon discount if applicable.
6. If amount=0 (free plan): insert ACTIVE subscription with startDate=now(), insert COMPLETED TenantPayment with amount=0, emit SUBSCRIPTION_CREATED BillingEvent, call syncTierToTenant(), return success
7. If amount>0 (paid plan): insert PENDING subscription, initialize gateway payment via PaystackService/PayPalService, insert PENDING TenantPayment with gateway reference, emit SUBSCRIPTION_CREATED BillingEvent, return paymentUrl for redirect
8. Wrap in `db.transaction()`
9. Generate subscription IDs with `crypto.randomUUID()`

**Step 4 — cancelTenantSubscription** (~50 lines):
Parameters: `{ tenantId, subscriptionId, reason? }`
Returns: `Promise<TenantBillingActionResult<{ subscriptionId, previousStatus }>>`

Logic:

1. Find subscription, verify it belongs to tenant
2. If already CANCELLED or EXPIRED, return error 409
3. Update status to CANCELLED, set cancelledAt=now(), cancelReason=reason
4. Emit SUBSCRIPTION_CANCELLED billing event
5. Do NOT change Tenant.tier on cancellation (tenant retains last tier until subscription fully expires or admin changes)

**Step 5 — upgradeTenantSubscription / downgradeTenantSubscription** (~80 lines each):
Parameters: `{ tenantId, subscriptionId, newPlanId }`
Logic:

1. Validate new plan exists
2. Validate subscription is ACTIVE and belongs to tenant
3. For upgrade: if new plan price > current plan price, create prorated BillingAdjustment (credit remaining days of old plan, charge new plan). For downgrade: schedule change for nextBillingDate OR apply immediately with credit.
4. Update subscription planId
5. Emit PLAN_UPGRADED or PLAN_DOWNGRADED event
6. Call syncTierToTenant() immediately
7. Return updated subscription

Simplification (ponytail): For MVP, upgrade/downgrade are immediate plan swaps without proration. Proration is deferred. The functions validate plan exists, update subscription.planId, emit event, sync tier. This avoids complex partial-month math.

**Step 6 — markTransactionCompletedByReference** (webhook handler, ~120 lines):
Parameters: `reference: string` (the gateway's externalRef)
Returns: `Promise<TenantBillingActionResult<{ transactionId, subscriptionId }>>`

Logic (ensure-record idempotent pattern):

1. Find TenantPayment by externalRef — if not found, return 404
2. If TenantPayment.status is already COMPLETED, return existing data (idempotent)
3. Find associated TenantSubscription
4. In transaction: update TenantPayment.status=COMPLETED, update TenantSubscription.status=ACTIVE (and startDate=now() if null), create TenantInvoice via ensureTenantInvoiceRecord(), emit PAYMENT_RECEIVED event
5. Call syncTierToTenant(tenantId)
6. Return success

**Step 7 — markTransactionFailedByReference** (~40 lines):
Same pattern as completed but sets status=FAILED, emits PAYMENT_FAILED event. Subscription remains PENDING.

**Step 8 — ensureTenantInvoiceRecord** (~100 lines):
Idempotent invoice creation. If invoice exists for transactionId, update and return. Otherwise insert new invoice with invoiceNumber from `deriveInvoiceNumber()` helper.

**Step 9 — getTenantBillingSnapshot** (~60 lines):
Parameters: `tenantId`
Returns: Current subscription, next invoice, payment methods count, recent transactions (last 5).
Used by Plan 04 tenant portal.

**Step 10 — recordBillingEvent** (~30 lines):
Helper to insert BillingEvent row. Used internally by all mutation functions.

**Step 11 — syncTierToTenant** (~40 lines):
Parameters: `tenantId: string`

1. Find ACTIVE TenantSubscription with its BillingPlan (join)
2. If no active subscription, do nothing (keep existing tier)
3. Check if tierManualOverride is true — if so, do nothing
4. If plan.tier differs from current tenant.tier: update tenants.tier to plan.tier, log with Pino
5. Log warning if tenant.tier is not in Tier enum (safety check)

1. `deriveInvoiceNumber(params: { tenantSlug: string }): string` — generates "INV-{tenantSlug}-{YYYYMM}-{random4}" format using `crypto.randomUUID().slice(0, 4)` for the random component. Example: "INV-soralia-202606-a3f2"

2. `addBillingCycleMonths(date: Date, months: number): Date` — adds N months to date, handling month-end edge cases (Jan 31 + 1 month = Feb 28/29).

4. `formatCurrency(amount: number, currency?: string): string` — e.g., formatCurrency(299) = "R 299.00".

5. `decimalToNumber(value: string | null | undefined): number` — converts Drizzle decimal column string to float.

| Threat ID | Category               | Component              | Disposition | Mitigation Plan                                                                                                                                |
| --------- | ---------------------- | ---------------------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |

| T-46.1-05 | Tampering              | Checkout price         | mitigate    | Server-side price lookup from BillingPlan table — client-sent price is ignored; amount is always derived from DB                               |
| T-46.1-06 | Denial of Service      | Duplicate checkout     | mitigate    | createTenantSubscriptionCheckout cancels existing ACTIVE/PENDING/TRIALING subscriptions before creating new one                                |
