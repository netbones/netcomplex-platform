## The Double-Default Problem

**Current code (DashboardPage.tsx line 91):**

```ts
const tabWidgets = userWidgets[activeTab] || currentTab?.defaultWidgets || [];
```

This creates two sources of truth for "which widgets appear on a tab by default":

1. **DEFAULT_TABS[].defaultWidgets** — hardcoded in DashboardPage.tsx (lines 21-58)
2. **useWidgetStore().userWidgets** — populated by getDefaultLayout() from Plan 01

When a new user first loads the dashboard:

- Store has `userWidgets: {}` (empty, no hydration from DB)
- Fallback fires: `currentTab?.defaultWidgets` → uses hardcoded list
- If store hydration completes AFTER initial render, `userWidgets` stays empty
  (because the hydration sets store but doesn't trigger re-render for already-resolved tabs)

**Solution:** DEFAULT_TABS keeps its tab identity (id, label, icon) but `defaultWidgets`
becomes unused for the fallback path. Instead, the fallback reads from getDefaultLayout(role).
This makes default-layouts.ts the single source of truth for initial widget lists.

**DEFAULT_TABS.defaultWidgets is NOT deleted** — it remains as a type-safe property
on the Tab interface and may be used by the tab rendering itself (e.g. tab badge counts).
But the widget rendering fallback on line 91 MUST read from the store or getDefaultLayout,
never from DEFAULT_TABS.defaultWidgets.
</double_default_problem>

<action>
Read widget-store.ts in full. Also read 29-01-SUMMARY.md to confirm the actual
export names from default-layouts.ts.

**Problem with current resetLayout():**
Line 177-178: `resetLayout: () => { set({ layouts: {}, userWidgets: {} }); }`
This clears the store to empty but does NOT persist to the database.
On next page load, hydrateFromDatabase fires, finds the old saved layout
in the DB, and restores it — the reset was ephemeral.

**Solution: Add `resetToRoleDefaults` action that:**

1. Clears layouts to `{}`
2. Seeds userWidgets from getDefaultLayout(role).userWidgets
3. Seeds layouts from getDefaultLayout(role).layouts
4. Calls saveToDatabase(userId) to persist the reset

**Implementation:**

1. Add import at top of widget-store.ts:

   ```ts
   import { getDefaultLayout } from '@widgets/dashboard/model/default-layouts';
   ```

   (Check barrel exports — if @widgets/dashboard re-exports it, use that path instead.
   If the import creates a circular dependency, use a lazy import pattern:
   `const getDefaultLayout = () => require('@widgets/dashboard/model/default-layouts').getDefaultLayout();`
   But prefer direct import if possible.)

2. Add to WidgetStore interface:

   ```ts
   resetToRoleDefaults: (role: string) => void;
   ```

3. Implement in the store creator:

   ```ts
   resetToRoleDefaults: (role: string) => {
     const defaults = getDefaultLayout(role);
     set({
       layouts: defaults.layouts,
       userWidgets: defaults.userWidgets,
     });
     // Persist to DB — need the userId. Get from session.
     // The store doesn't have userId, so we need to either:
     //   a) Pass userId as second parameter, or
     //   b) Have DashboardPage call saveToDatabase after resetToRoleDefaults
     //
     // Option (a) is cleaner — one call from the consumer:
     //   resetToRoleDefaults(role, userId)
   ```

   Actually, `saveToDatabase` already takes a `userId` parameter. The cleanest
   approach is to make `resetToRoleDefaults` accept both role and userId:

   ```ts
   resetToRoleDefaults: (role: string, userId: string) => {
     const defaults = getDefaultLayout(role);
     set({
       layouts: defaults.layouts,
       userWidgets: defaults.userWidgets,
     });
     // Use setTimeout to ensure state is set before persisting
     setTimeout(() => {
       get().saveToDatabase(userId);
     }, 0);
   };
   ```

4. Update the WidgetStore interface:

   ```ts
   resetToRoleDefaults: (role: string, userId: string) => void;
   ```

5. Update DashboardPage.tsx Task 1 accordingly — pass userId:
   ```ts
   onResetLayout={() => {
     const role = session?.user?.role || 'RESIDENT';
     const userId = session?.user?.id;
     if (userId) resetToRoleDefaults(role, userId);
     setIsEditMode(false);
   }}
   ```
   (The userId check prevents calling reset without a session.)

**Do NOT modify `resetLayout()` or `resetTabToDefaults()`** — they may be used
elsewhere. Add `resetToRoleDefaults` as a new method alongside them.

**Circular dependency check:** widget-store.ts importing from
@widgets/dashboard/model/default-layouts creates a dependency from
entities → widgets. Check if this violates the project's layering.
If it does, move default-layouts.ts to @entities/widget/model/ instead
(Plan 01 Task 3 creates it, so adjust the path there too if needed).
The key principle: default layout data is configuration, not UI.
It belongs closer to the store than to the widget components.
