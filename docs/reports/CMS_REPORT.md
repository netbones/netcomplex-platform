# Soralia Village CMS Audit Report

> **Date:** 2026-07-11  
> **Scope:** TipTap-based content management system vs. industry headless CMS platforms  
> **Generated by:** Architecture audit — codebase analysis + competitor research

---

## 1. Executive Summary

Soralia Village runs a **custom-built CMS** powered by TipTap (v3.21), PostgreSQL (Supabase), and a multi-locale content model. It is a well-architected, feature-rich system that outperforms expectations for a custom build — with multi-locale editing, media management, soft deletes, scheduled publishing, and moderation workflow already in place.

**Compared to dedicated CMS platforms, we are missing: content versioning/revision history, block-based composable editing, collaboration, tables, links, and audit logging.** These gaps are meaningful but none are showstoppers for M5 launch. The system is robust for a community platform; the primary hardening need is version history.

**Recommendation:** No platform migration warranted. Address the top-5 gaps through incremental TipTap extension adoption and a lightweight revision table. Re-evaluate at M6+ when multi-tenant content complexity grows.

### 2.3 Content Model (`Content` table)

```typescript
{
  id, tenantId, title (jsonb), content (jsonb), excerpt (jsonb),
  image (text), category (enum, 8 values), tags (text[]),
  authorId (FK→User), groupId (FK→Group),
  published (boolean), featured (boolean), priority (text),
  defaultLocale (text), contentType (text: article/campaign/document),
  license (enum, 5 values), copyrightHolder (text),
  moderationStatus (enum: DRAFT/PUBLISHED/UNPUBLISHED/FLAGGED),
  viewCount (int), commentsEnabled (boolean),
  createdAt, updatedAt, publishedAt, expiresAt, deletedAt
}
```

**Multi-locale model:** JSONB columns (`title`, `content`, `excerpt`) store `{ "en": "...", "af": "...", "xh": "...", "zu": "..." }`. Content is TipTap HTML strings per locale. Localization via `getLocalizedContent()` with locale fallback chain.

**Related tables:** `ContentLike` (one-to-many, `@@unique([contentId, userId])`), `Announcement` (separate table, plain text, no rich editor).

### 2.4 Publishing & Moderation

| Feature                  | Implementation                                                           |
| ------------------------ | ------------------------------------------------------------------------ |
| **Draft/Publish**        | `moderationStatus` enum + `published` boolean, auto-synced on moderation |
| **Scheduled publishing** | `publishedAt` timestamp, content hidden from non-admins before date      |
| **Auto-expiry**          | `expiresAt` timestamp, content hidden from non-admins after date         |
| **Soft delete**          | `deletedAt` timestamp, queries filter `WHERE deletedAt IS NULL`          |
| **Moderation**           | Admin page with Publish/Unpublish/Flag inline actions                    |
| **Permissions**          | `content` (full access + moderate), `contentOwn` (own content only)      |

### 2.5 Media Management

- **Upload endpoint:** `/api/upload` — FormData → S3 (`users/{userId}/{uuid}.{ext}`), 2MB limit, JPEG/PNG/GIF/WebP
- **Media Library:** `/api/media` — list/delete user images, `MediaLibrary.tsx` component with grid/carousel views + drag-drop upload
- **In-editor flow:** toolbar button → file input → upload → `setImage({ src: url })`; or media library modal → select → insert

### 2.6 Security

- **DOMPurify sanitization** on client (`src/shared/lib/sanitize/index.ts`) and server (`src/shared/lib/sanitize/server.ts` with JSDOM)
- **Rate limiting** on `createContent` (5/min)
- **CSRF protection** via Honeypot in `ContentForm`
- **File validation** — max 2MB, allowed types enforced both client and server
- **Permission-gated** — all content mutations require `content` or `contentOwn` permission
- **Multi-tenant isolation** — all queries scoped to `tenantId`

## 4. Strengths of Our System

### 4.1 Architecture Wins

1. **Deep Next.js integration** — Server Components, ISR with tag-based revalidation, Streaming/Suspense. No separate admin app to deploy or maintain.

2. **Multi-locale from the ground up** — JSONB `{ en, af, xh, zu }` is cleaner than most CMS "locale per entry" models. Single content item carries all translations; locale resolution is a query-time concern via `getLocalizedContent()`.

3. **tRPC + REST dual API** — Internal consumers get type-safe tRPC; external integrations get standards-compliant REST. Most CMS platforms pick one.

4. **Soft-delete pervasive** — `deletedAt` timestamps with `notDeleted()` query filter on every read. Ghost and Directus don't do this natively.

5. **Flexible content types** — `contentType` field (`article`, `campaign`, `document`) extends the model without schema changes. Ghost has no custom content types at all.

6. **No vendor lock-in** — Own the database, own the code. Contentful/Sanity lock content in their platform; we can migrate freely.

7. **FSD architecture** — Content is an `entities` slice with clear public API, server-only exports, DTOs. Adding new content features follows established boundaries.

8. **Permission model** — `content` vs `contentOwn` is better than Strapi's all-or-nothing free-tier RBAC and Ghost's fixed 5 roles.

## 5. Critical Gaps & Remediation

### 5.1 Gap #1: Content Versioning (HIGH)

**Problem:** No revision history. Every save overwrites the previous state. No rollback, no diff, no audit trail of who changed what.

**Impact:** Board members editing policy documents, admins updating announcements — a single mistake is irreversible. Violates basic content governance expectations.

**Payload comparison:** Payload has `_slug_versions` collections with autosave, diffs in admin UI, restore to any version, access control on readVersions.

**Remediation options:**

| Option                                    | Effort           | Description                                                                                                                                                                                                         |
| ----------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. Lightweight `ContentVersion` table** | ~3 days          | New table: `{ id, contentId, version (int), snapshot (jsonb), userId, createdAt, changeSummary (text) }`. Trigger on PATCH: increment version, snapshot prior state. Admin page: list versions, view diff, restore. |
| **B. TipTap Version History (Pro)**       | ~1 day + license | TipTap Pro extension tracks versions within the editor session. Pairs with Y.js. Less durable (in-app, not DB-persisted) but lower effort.                                                                          |
| **C. Database trigger + audit table**     | ~2 days          | PostgreSQL trigger writes old row to `content_history` on UPDATE. No app changes needed for capture. Still needs UI for viewing/restoring.                                                                          |

**Recommendation:** Option A (ContentVersion table). DB-persisted, survives editor session boundaries, works with existing API patterns. Implement as a separate BD issue post-M5.

### 5.2 Gap #2: Audit Logging (HIGH)

**Problem:** No record of what admin performed which moderation action, who published/unpublished content, or who edited what.

**Impact:** Compliance/accountability gap. Cannot answer "who flagged this article?" or "who unpublished the conservation notice?"

**Remediation:** Add `ContentAuditLog` table: `{ id, contentId, userId, action (enum: CREATED/UPDATED/PUBLISHED/UNPUBLISHED/FLAGGED/DELETED/RESTORED), metadata (jsonb), createdAt }`. Insert on every content mutation. Surfacing in admin UI is optional for MVP; queryable via SQL is sufficient for audit needs.

### 5.3 Gap #3: Tables in Rich Text (MEDIUM)

**Problem:** Community content frequently needs tabular data — event schedules, fee comparisons, committee rosters. TipTap has `@tiptap/extension-table` available; it's simply not installed.

**Remediation:** Install `@tiptap/extension-table` + `@tiptap/extension-table-row` + `@tiptap/extension-table-header` + `@tiptap/extension-table-cell`. Add toolbar buttons (Insert Table, Add Row/Column, Delete Table). Update `RichTextRenderer` to render tables. ~1 day.

### 5.4 Gap #4: Hyperlinks (MEDIUM)

**Problem:** No link button in the toolbar. Users cannot create hyperlinks in rich text content.

**Impact:** Community articles cannot reference external resources, link to other pages, or cite sources inline.

**Remediation:** `@tiptap/extension-link` is already in the starter-kit dependency tree. Add a link toolbar button with URL input modal. Update `RichTextRenderer` to render `<a>` tags. Ensure DOMPurify allows `href` with `target="_blank"` and `rel="noopener noreferrer"`. ~2 hours.

### 5.5 Gap #5: Block-Based Composable Editing (MEDIUM)

**Problem:** Content is monolithic rich text. Users cannot embed structured content blocks (event cards, survey embeds, resource links) inline within articles.

**Payload comparison:** Payload's `BlocksFeature` lets editors drop configured blocks into rich text via slash commands.

**Sanity comparison:** Sanity's Portable Text has custom block types that render as rich interactive components.

**Remediation:** This is the most impactful feature gap. TipTap supports custom Node extensions — we can build domain-specific blocks:

```
/event    → inserts EventCard node (renders event details inline)
/survey   → inserts SurveyEmbed node (renders survey widget)
/resource → inserts ResourceLink node (renders resource card)
/poll     → inserts PollBlock node (renders live poll)
```

Implementation pattern: Custom TipTap Node extension → toolbar slash-command menu → `RichTextRenderer` node handler → renders the actual widget component. This is a multi-day feature best planned as a GSD phase post-M5.

### 5.6 Gap #6: Content Releases / Grouped Publishing (LOW)

**Problem:** Publishing a coordinated set of content (e.g., monthly newsletter with 3 articles + 1 announcement) requires manually publishing each item individually.

**Sanity/Payload/Strapi comparison:** All three support "Releases" — group content items, schedule simultaneous publication.

**Remediation:** Add `ContentRelease` table: `{ id, name, scheduledAt, status, items: [{ contentId }] }`. Single "Publish Release" action sets `publishedAt` on all items to the release time. Lower priority for M5.

### 5.7 Gap #7: Image Transformations (LOW)

**Problem:** Images uploaded at full resolution, served at full resolution. No responsive sizes, no focal-point cropping, no WebP auto-conversion.

**Payload comparison:** Payload's Sharp integration generates multiple sizes with focal-point-aware cropping on upload.

**Remediation:** If Supabase Storage adds image transformation (in beta as of 2026), adopt that. Otherwise, integrate `sharp` on the server to generate thumbnail/medium/large variants on upload. Store variants in S3 alongside original. ~2 days.

## 7. Migration Analysis: Should We Switch?

### 7.1 When to Consider a Platform

| Trigger                                                     | Relevant?                                                |
| ----------------------------------------------------------- | -------------------------------------------------------- |
| Building a custom editor is consuming significant dev time  | ❌ — TipTap is already integrated and working            |
| Need enterprise workflows (multi-stage review, SCIM, SSO)   | ❌ — Not for a community platform at this scale          |
| Content team is non-technical and needs a polished admin UI | ⚠️ — Our admin UI is functional but not Contentful-grade |
| Need real-time collaborative editing                        | ⚠️ — TipTap Collaboration (Pro) exists if we need it     |
| Managing 100+ content types                                 | ❌ — We have 1 content table with a type discriminator   |
| Multi-tenant at scale (50+ tenants)                         | ⚠️ — Could become pain point at M6+, re-evaluate then    |

### 7.2 If We Were to Switch: Best Fit

**Payload CMS** is the strongest candidate:

- Next.js native (drops into our app, no separate deploy)
- TypeScript throughout (matches our stack)
- Lexical editor with BlocksFeature (matches our need for composable blocks)
- Self-hosted, MIT license, no vendor lock-in
- Granular field-level access control (matches our permission model)

**Why not now:** The migration cost (schema migration, editor retraining, API rewrite) far exceeds the value of filling our ~7 gaps natively. We have 80% of Payload's feature set already built.
